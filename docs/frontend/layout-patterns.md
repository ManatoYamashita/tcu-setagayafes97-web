# レイアウトパターンと設計原則

Header と Hero の寸法、z-index のレイヤー、`position` の使い分け、寸法を1か所で持つ原則。
レスポンシブの帯とヒーロー画像は [layout-responsive.md](./layout-responsive.md)、
幅の梯子・左端の揃え方・負のマージン・Tailwind v4 の出力順は
[layout-width-and-alignment.md](./layout-width-and-alignment.md) にある。

## Header と Hero

Header（`src/components/layout/Header.tsx`）は `sticky top-0 z-40` で、**フロー上に高さを占有する。**
**special 以外の全ページのヒーローは compact（`h-[52svh] min-h-[360px] lg:h-[50svh]`）で揃える。**
`PageHero` / `PageSheetLayout` の既定値が compact で、トップ（`HeroSection`）と委員会（`AboutHero`）も同じ値を持つ。
`/special` だけが `heroSize="default"`（70svh）、`SpecialHero` だけが全画面（`calc(100svh - var(--header-height))`）を保つ。
`--header-height` の一次定義は `src/app/globals.css` の1箇所で、いま参照するのは `SpecialHero` と 404 など。

以降の全画面ヒーローの実測値・注意は、`SpecialHero` と、compact 化する前のトップ・委員会の記録として読むこと。

2026-09-30 に本番トップで実測した値（詳細は [agent-browser-workflow.md](./agent-browser-workflow.md)）:

| viewport  | Header の実高 | Hero の top | Hero の高さ | 内訳                           |
| --------- | ------------- | ----------- | ----------- | ------------------------------ |
| 1920×1080 | 107           | 107         | 992         | 1080 − 88（`--header-height`） |
| 768×1024  | 107           | 107         | 936         | 1024 − 88                      |
| 375×667   | 107           | 107         | 579         | 667 − 88                       |

**Hero の高さは「viewport − Header の実高」ではない。** 理由は次節。

### `--header-height` は2状態ヘッダーの近似値である

Header は `isAtTop` で高さが変わる2状態コンポーネントである。
`--header-height`（現在 `5.5rem` = 88px）はこの2状態の中間に置かれた近似値であり、
どちらの実測値とも一致しない。

| 状態                      | 内訳                                     | 実測高さ  |
| ------------------------- | ---------------------------------------- | --------- |
| `isAtTop`（スクロール前） | `pt-0` + `py-3`×2 + ロゴ `h-[83px]`      | **107px** |
| スクロール後（ピル型）    | `pt-2` + `py-3`×2 + ロゴ `h-[45px]`      | **77px**  |
| `--header-height`         | 変数定義（コメントはロゴ56px前提で古い） | 88px      |

このため `calc(100svh - var(--header-height))` のヒーローは、
初期表示（`isAtTop`）で下端が折り返し線の **約19px下** に沈む。
下寄せレイアウトのヒーローでも `pb-10`（40px）程度の下パディングがあれば
中身は画面内に残るため実用上の問題はないが、
**「ヒーロー下端がぴったり折り返し線に一致する」前提の実装をしてはいけない。**

厳密な一致が必要になった場合は、変数を1つの静的値で持つ方式自体を見直すこと
（`isAtTop` の状態を CSS 変数へ書き出す等）。ヒーロー側で個別に数値を
ハードコードして辻褄を合わせるのは、変更漏れを増やすだけなので禁止する。

### 全画面ヒーローの実装は3箇所で統一する

（現在は `SpecialHero` のみ。トップと委員会は compact 化済み）`HeroSection`（トップ）・`AboutHero`（委員会）・`SpecialHero`（著名人企画LP）は
いずれも `calc(100svh - var(--header-height))` を使っていた。

Header は `sticky` であり **フロー上に高さを占有する**。
`fixed` ではないため、ヒーローに単純な `100svh` を与えると
ヘッダーの高さぶんだけ全体が下へ押し出され、下端が画面外へ出る。
特に `SpecialHero` は `items-end` でロゴと主催者名を下寄せするため、
`min-h-svh` にすると初期表示でロゴが切れる（813×656 で実測: ロゴ下端が3px、
主催者名は全体が画面外）。

`SpecialHero` のみ `h` ではなく `min-h` を使う。
長いアーティスト名がロゴ画像なしで入稿された場合に、
高さを固定するとテキストが溢れるためである。

## z-index のレイヤー

**スケールの値だけを使う。アドホックな値（`z-[45]` など）は使わない。**
ページ全体の層として使われている値は次のとおり（2026-09-30 に `src/` を数えた。数え方は節末）。

| z-index | 層                                  | 実例                                                           |
| ------- | ----------------------------------- | -------------------------------------------------------------- |
| 60      | ページ全体を覆うオーバーレイ        | オープナー（`Opener.tsx`）                                     |
| 50      | Header より上に出す固定 UI          | スキップリンク（`Header.tsx`）、下書きバナー、モバイルメニュー |
| 40      | Sticky Header                       | `Header.tsx`                                                   |
| 30      | Hero 内の最上位（浮遊要素・見出し） | トップの Hero の見出しほか                                     |
| 20      | コンテンツの上位レイヤー            | テキストエリア、カードの上位                                   |
| 10      | コンテンツのベースレイヤー          | 画像、背景、カードのベース                                     |
| auto    | 通常のコンテンツ                    | 指定しない                                                     |

> [!IMPORTANT]
> **z-index が効くのは同じ積み重ね文脈の中だけである。** ナビのドロップダウン（`NavDropdown.tsx`）と
> 言語切替（`LanguageSwitcher.tsx`）は `z-60` だが、`sticky` かつ `z-40` の Header が積み重ね文脈を作るため、
> **ページ全体で見れば Header と同じ高さ（40）にいる。** z-50 の固定 UI より上には出ない。
> 逆に、ページ全体の最前面に出したい要素は Header の外（ルートの積み重ね文脈）に置く。

> [!NOTE]
> 以前この文書のスケールには 50 が無く、「Header 以外で z-40 以上を使わない」としていたが、
> 実装はスキップリンクなど3つで z-50 を使っていた。オープナーは規則外の `z-[51]` だったため、
> 2026-09-30 に `z-60` へ揃えた（オープナーの親は積み重ね文脈を作らないので、重なり順は変わらない）。

### 現存する例外（未整理）

スケール外の値が次の箇所に残っている。いずれも**1つのコンポーネントの中で層の順番を付けるためのもの**で、
ページ全体の層ではない。規則に合わせるかどうかは未決定である。

| 値             | 箇所                                                    | 用途                                                         |
| -------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| `z-[1]`        | `AboutHero.tsx`（2箇所）                                | 上下のマスク                                                 |
| `z-[9]`        | `FeaturedCarousel.tsx`（2箇所）                         | カード下部のぼかし・オーバーレイ                             |
| `z-[5]`        | `StaggeredMobileMenu.tsx`（1箇所）                      | メニューの前段レイヤー                                       |
| `z-0`          | 8箇所                                                   | 積み重ね文脈を作るための基準                                 |
| `z-index: 100` | `globals.css` の `::view-transition-group(site-header)` | View Transition 中にヘッダーを前面へ（文書の積み重ねとは別） |

**数えるときは角括弧の任意値を取りこぼさないこと。** `\bz-[0-9]+\b` のような語境界つきの正規表現は
`z-[1]` に一致しない（2026-09-30、最初の集計でこれを踏み、例外が無いと書きかけた）。

```bash
grep -rnoE '[a-z:-]*z-\[[^]]+\]' src                                      # 任意値
grep -rhoE '(^|[^a-z0-9-])z-[0-9]+' src | grep -oE 'z-[0-9]+' | sort | uniq -c  # 数値クラス
grep -rnE 'z-index[[:space:]]*:|zIndex[[:space:]]*:' src                   # CSS とインラインスタイル
```

ブラウザ上の実際の並びは [agent-browser-workflow.md](./agent-browser-workflow.md) の「z-index の一覧」スニペットで確かめられる。

## position の使い分け

### position プロパティの特性

| position   | 配置基準                   | スクロール挙動         | 用途例                       |
| ---------- | -------------------------- | ---------------------- | ---------------------------- |
| `static`   | 通常フロー                 | 通常                   | デフォルト                   |
| `relative` | 通常位置からのオフセット   | 通常                   | absolute子要素の基準点       |
| `absolute` | 最も近いpositioned親要素   | 親要素に追従           | Hero内の浮遊要素（バッジ等） |
| `fixed`    | viewport                   | 画面固定（追従しない） | モーダル、トースト           |
| `sticky`   | 最も近いスクロールコンテナ | 閾値まで通常、以降固定 | スティッキーヘッダー         |

- **Hero 内の浮遊要素**は、親の `section` に `relative` を置いて `absolute` で配置し、`z-30` 以下に収める
- **ページ全体を覆う要素**（モーダル・オーバーレイ）は `fixed inset-0` で、上の表のどの層に置くかを先に決める

## 百分率の高さは親の height が確定しているときだけ

`height: %`（Tailwind の `h-full`）は、**親の高さが確定しているときにしか解決されない。**
`min-height` は親の高さを確定させないため、次は `0px` になる。

```tsx
<div className="relative" style={{ minHeight: "600px" }}>  {/* height を持たない */}
  <div className="h-full">                                  {/* → 0px */}
    <div style={{ top: "37.5%", height: "18.75%" }} />      {/* → 全部 0px 基準 */}
```

タイムテーブルのガント盤面はこれで全企画が同一座標に重なっていた（#148）。
絶対配置の子しか持たない要素は、高さが `auto` に落ちた時点で 0 になる。

**座標計算を伴う面は、高さを数値（px）で持たせること。** 詳細と、そこから派生する
`overflow-x: auto` / `sticky` の制約は [timetable-gantt.md](./timetable-gantt.md) を参照。

## 同じ寸法を CSS と JS が別々に持たない

ある寸法を **CSS 側（Tailwind クラス）と JS 側（定数）の両方が持っている**とき、
それは1つの値ではなく、たまたま今は一致している2つの値である。
**片方だけ変えられる構造になっている時点で、いずれ食い違う。**

コメントで「両方を合わせること」と書いても防げない。守るべきなのは規律ではなく構造で、
**実体を1つにして、もう片方をそこから導出させる**しかない。

### 実例1: 親の高さ（#148）

盤面の高さを CSS（`min-height`）が持ち、子の座標を JS（`top: %`）が持っていた。
`min-height` は高さを確定させないため `%` が解決されず、全企画が同一座標へ潰れた。

→ 高さの実体を JS の数値に一本化し、`style={{ height: 数値 }}` で CSS へ渡す。

### 実例2: カード間の余白（#154）

カード間の余白を CSS（`pb-1`）が持ち、密度判定の閾値計算を JS（`CARD_GAP_PX`）が持っていた。
どちらも 4px だが繋がっておらず、判定側が「枠」と「カード実寸」を取り違えていることに
気付ける仕組みが無かった。

```tsx
// 悪い: 4px が2箇所にあり、片方だけ動かせる
<div className="absolute px-1 pb-1" style={{ height: slotPx }}>
  <Card density={getCardDensity(slotPx)} />   {/* pb-1 を引いていない */}

// 良い: 実体は定数1つ。CSS はそこから受け取る
<div className="absolute px-1" style={{ height: slotPx, paddingBottom: CARD_GAP_PX }}>
  <Card density={getCardDensity(slotPx)} />   {/* 内部で CARD_GAP_PX を引く */}
```

### 判断の手順

1. その寸法を使う箇所を全て挙げる。CSS クラス・インラインスタイル・JS 定数を区別する
2. 2箇所以上が**独立に**値を持っていれば、実体をどちらか一方へ寄せる
3. 寄せ先は原則 JS 側。計算に使えて、`tsc` が参照の取り残しを見つけられる
4. Tailwind クラスで表現できなくなることを損失と考えない。
   **クラス名の統一より、値が1つであることのほうが強い保証である**

なお、Tailwind の任意値（`h-[var(--x)]`）で CSS 変数を経由させる手もあるが、
その値を JS 側でも計算に使うなら、変数を介さず数値を直接渡すほうが追跡しやすい。

## `svh` を使う（`vh` は使わない）

モバイル Safari では `100vh` が URL バーを含む高さになり、実際の表示領域より大きい。
**全画面ヒーロー（現在は `SpecialHero`）は `100svh` を使う**（前節「全画面ヒーローの実装は3箇所で統一する」）。compact のヒーローも `svh` である。

| 単位     | 意味                               | 用途                                   |
| -------- | ---------------------------------- | -------------------------------------- |
| `100svh` | URL バーが表示されている状態の高さ | 全画面ヒーロー（本プロジェクトの標準） |
| `100dvh` | URL バーの表示に追従して変わる高さ | 追従が必要な場合だけ                   |
| `100vh`  | URL バーを含む高さ                 | 使わない                               |

**`100vh` へのフォールバックは書かなくてよい。** `100svh` は Safari 15.4 / Chrome 108 以降で使え、
本プロジェクトの下限（TailwindCSS v4 が要求する Safari 16.4 / Chrome 111）はそれより新しい。
