# `/events` の建物の絞り込み

企画の「建物」をどこから決め、`/events` の「建物」の選択肢・絞り込み・URL の検証・
関連企画・検索へどう流すかをまとめる。キーワード検索と正規化は
[events-search.md](./events-search.md) が扱う。

| ファイル                     | 役割                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `src/lib/events.ts`          | `normalizeEventBuildings()`（microCMS の `buildings` の正規化）              |
| `src/data/filter-options.ts` | `getEventBuildings()`（企画の建物）、`sortBuildingIds()`（並び順）           |
| `src/lib/filters.ts`         | `collectBuildingIds()` / `listBuildingOptions()`、絞り込み、URL クエリの検証 |

## 建物の出どころ

| 入力                            | 型                             | 扱い                                                                         |
| ------------------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| microCMS「建物」（`buildings`） | select・**複数選択**・**必須** | **唯一の出どころ。** 値は `9号館` のような素の名前（`値 : ラベル` ではない） |
| microCMS「場所」（`place`）     | text                           | 表示用の細かい場所（`11A`、`テント5` など）。**建物の判定には使わない**      |

**企画の建物は、必ず `getEventBuildings(event)` を通して読む。**

1. `buildings` が空でなければ、それを返す
2. 空なら `[その他]` を返す（管理画面では必須なので、空になるのは API で直接書いたときなど）

**`place` からの推定は #467 の後片付けで撤去した**（2026-10-12）。移行期間は `place` の表記から
号館を推定して空欄を補っていたが、全102件に値が入り「建物」を必須にしたため不要になった。
推定は `13D/13E` や `1BJ` のような表記を取りこぼし、11件を「その他」へ落としていた。

`normalizeEventBuildings()` は、未入力（API は `[]` を返す。キーが無い場合も同じ扱い）を `[]` にし、各値の前後の空白を落とし、
空文字と重複を除く。`readSelectKey()` は通さない（`:` で割らない）。

> [!IMPORTANT]
> **`event.buildings` を直接読まないこと。** 未入力の企画が「どの建物にも属さない」扱いになり、
> 絞り込み・選択肢から消える。`getEventBuildings()` は空配列を返さない（最低でも `その他`）。

### `その他`

`OTHER_BUILDING_ID`（`その他`）は microCMS の選択肢 `その他` と同じ文字列である。
値の無い企画と、明示的に `その他` を選んだ企画が同じ選択肢にまとまる。
建物名ではなく振り分け先の名前なので、関連企画の一致・キーワード検索・意味検索には使わない。

## microCMS の選択肢（2026-10-11 作成）

`1号館`〜`10号館`、`第1アリーナ`、`第3アリーナ`、`図書館`、`屋外`、`ホール`、`グラウンド`、`その他` の17個。
**`体育館` は作っていない**（`9号館 体育館(第1アリーナ)` は `第1アリーナ` に揃える）。
2026-10-12 に**必須 ON** にした（全102件の入力を確かめた後）。

**入稿ルール: 号館の中にある名前の付いた会場は、号館も一緒に選ぶ**（`9号館` + `第1アリーナ`、`7号館` + `ホール`）。
コードに親子関係は無いので、片方だけだと号館の絞り込みに出ない。

管理画面での実測（2026-10-11。検証用の選択肢と非公開の下書きで試し、両方とも削除済み）:

| 操作                                  | 保存済みの値（draftKey 付きの API で確認）            |
| ------------------------------------- | ----------------------------------------------------- |
| 選択肢を改名（`検証用A` → `検証用B`） | **新しい名前で返る。** 選択肢は内部IDで紐づいている   |
| 選択肢を削除（`検証用C`）             | **応答から消える。** 選んでいた企画は警告なく値を失う |
| 「複数選択」の ON/OFF                 | 作成後は切り替えられない（スイッチが無効）            |

**改名は安全だが、削除は企画から値を黙って消す。** 選択肢を消す前に、その値を使う企画が無いかを確かめること。

## 選択肢はデータから作る

`listBuildingOptions(events)` は、**全企画の建物の和集合**（`collectBuildingIds()`）から
選択肢を作る。microCMS で選択肢を足し、企画に付ければ、コードを直さずに `/events` へ出る。
企画が1件も無い建物は出さない（`src/lib/timetable.ts` の `listStageTabs()` と同じ設計）。

### 並び順（`sortBuildingIds()`）

| 順  | 群               | 群の中の順                           | 例                                    |
| --- | ---------------- | ------------------------------------ | ------------------------------------- |
| 1   | `N号館`          | 数字の順（`10号館` は `9号館` の後） | `1号館` `9号館` `10号館`              |
| 2   | `第Nアリーナ`    | 数字の順                             | `第1アリーナ` `第2アリーナ`           |
| 3   | 名前の付いた場所 | `NAMED_BUILDING_ORDER` の順          | `図書館` `屋外` `ホール` `グラウンド` |
| 4   | 表に無い名前     | 出てきた順（安定ソート）             | 委員会が新しく足した名前              |
| 5   | `その他`         | —                                    |                                       |

**漢字の名前は読みの順に並べられない。** `localeCompare("ja")` / `Intl.Collator("ja")` は
単語の読みを見ない。実測（2026-10-11 / Node 22・ICU 77.1）で `屋外` `体育館` `図書館` は
`屋外 → 図書館 → 体育館` に並ぶ（読みの順なら `おくがい → たいいくかん → としょかん`）。
そこで名前の付いた場所だけはコードに短い順序表を持つ。
**表に無い名前は `その他` の直前に並ぶだけで、選択肢から消える経路は無い。**

### 2箇所で作る

`src/app/events/(list)/page.tsx` は `<Suspense>` の fallback 用に、`EventsContent` は本描画用に、
それぞれ同じ `listBuildingOptions()` を呼ぶ。page.tsx は `useSearchParams()` を読まない設計（#156）
なので、本描画側の値を降ろすことはできない。どちらも同じ全企画から作るので中身は一致する。

## 絞り込み

`?building=X` は「`getEventBuildings()` に `X` を含む企画」。`["9号館", "第3アリーナ"]` の企画は、
`9号館` と `第3アリーナ` のどちらを選んでも出る。

## URL クエリの検証

`parseEventFilters(params, events)` は `?building=` を**データに存在する建物**
（`collectBuildingIds(events)`）で照合する。存在しない値は `"all"` へ倒す
（`?building=99号館` を無言の0件にしない）。

**選択肢と検証は同じ集合から作るので、URL で受け付けた建物は必ず選択肢にある。**
選択肢に無い値を `<select>` の `value` に渡すと、表示が「すべて」へ化けたまま0件が並ぶ（#207）。
microCMS の選択肢にはあるが企画が1件も無い建物（`?building=グラウンド` など）も、「すべて」へ倒れる。

`parseEventFilters()` を呼ぶのは `EventsContent`（`useSearchParams()` を読む唯一の場所）だけで、
全企画は props の `initialEvents` から渡す。`/events` の静的HTMLの構造は変わらない。

## 関連企画・検索

| 箇所                                     | 建物の使い方                                                         |
| ---------------------------------------- | -------------------------------------------------------------------- |
| 関連企画（`RelatedEvents.tsx`）          | 共通する建物が1つ以上あれば「同じ建物」。`その他` 同士は一致としない |
| キーワード検索（`src/lib/search.ts`）    | `その他` を除く全建物を1つの項目にまとめ、重み3で照合                |
| 意味検索（`src/lib/semantic-search.ts`） | `その他` を除く全建物を `、` で繋いで `building` に載せる            |

## 入れなかったもの（#467 で判断済み）

- **親子関係**（`第3アリーナ` を選んだら `9号館` も付いたことにする）は入れない。入稿ルールで両方を選ぶ（上記）
- **タイムテーブルの列分け**（`src/data/stages.ts`）は `place` から決めたままにする（2026-10-12）。
  「建物」で分けても結果は同じ（`ホール` 11件・`第1アリーナ` 4件）で、祭り直前にテスト用データと
  E2E を作り直す危険に見合わない。第98回で再検討する
