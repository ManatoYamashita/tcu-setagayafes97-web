# `/events` の検索と絞り込み

`/events` のキーワード検索・建物フィルタの設計と、そう決めた理由をまとめる。
実装は次の5ファイルに分かれている。

| ファイル                       | 役割                                                                    |
| ------------------------------ | ----------------------------------------------------------------------- |
| `src/lib/text.ts`              | 正規化（`normalizeText` / `stripHtml`）。**検索と建物導出の共通の入口** |
| `src/data/search-stopwords.ts` | 文章クエリの区切り語・不要語                                            |
| `src/lib/search.ts`            | 3段カスケードの検索（`tokenizeQuery` / `searchEvents`）                 |
| `src/data/filter-options.ts`   | 建物の定義と `resolveBuildingId()`                                      |
| `src/lib/filters.ts`           | URL クエリの検証、絞り込み、選択肢の組み立て                            |

## 出発点: コードが実データと食い違っていた

2026-09-06 に microCMS の公開データ18件を実測した結果。

| フィールド                           | 実態                    | 当時のコードの前提                    |
| ------------------------------------ | ----------------------- | ------------------------------------- |
| `building`（建物番号 / text / 任意） | **18件すべて未入力**    | `string` 必須・完全一致で絞り込み     |
| `organizer` / `description`          | 3件欠落                 | `string` 必須                         |
| `content`                            | 16件欠落                | `string` 必須                         |
| `place`（場所 / text / 必須）        | 全件入力済み            | **絞り込みに一切使われていない**      |
| `type`                               | `store : 模擬店` が実在 | ホワイトリストに無く `other` へ落ちる |

`place` の実値。**自由入力なので表記が揺れる。**

```
TCUホール ×10 / 9号館アリーナ ×2 / ９号館アリーナ（全角）×1
11D / 61C / SAKURA GARDEN / テント１ / 世田谷キャンパス第１アリーナ␣（末尾に全角空白）
```

結果として、建物フィルタは選択肢を14個出しながら**どれを選んでも0件**だった。
キーワード検索は `undefined.toLowerCase()` で例外を投げていた（#166。例外自体は
PR #199 が `normalizeEvent()` の既定化で塞いだ）。

> [!IMPORTANT]
> **`building` は今後も埋まらない前提で設計している。** 入稿の運用を増やさずに
> 絞り込みを成立させるため、判定は `place` からの導出を主系とし、`building` が
> 入っていた場合だけそちらを優先する（`resolveBuildingId()` の解決順1）。

## 正規化はひとつの関数に集約する

`normalizeText()` が次の4段を通す。

1. NFKC — `９`→`9`、`ＴＣＵ`→`TCU`、`ﾎｰﾙ`→`ホール`、全角空白→半角空白
2. 小文字化
3. カタカナ→ひらがな — `ダンス` と `だんす` を同一視
4. 記号の除去と空白の畳み込み（**長音符 `ー` も落とす**。`ホール` と `ホル` を同一視する）

> [!WARNING]
> **検索と建物導出で別々に正規化してはいけない。** 片方だけ通すと
> 「検索ではヒットするのに建物フィルタでは落ちる」という食い違いが生まれる。
> `src/data/filter-options.ts` が `@/lib/text` を import しているのはこのため
> （data → lib の依存はこの1本だけに留めてある）。

`normalizeText(undefined)` は空文字を返す。**欠落フィールドの吸収をここでやる**のが要点で、
呼び出し側に `?.` を撒くと、同じ前提に依存する別の箇所が守られない。

## キーワード検索は3段カスケード

日本語は分かち書きしないため、文章をそのまま部分一致に掛けると必ず0件になる。
かといって助詞で機械的に割ると `のど自慢` が `ど自慢` になる。**上の段から順に試し、
1件でも当たったらそこで打ち切る**構造でこの2つを両立させている。

| 段  | 判定                                                        | これで拾えるもの              |
| --- | ----------------------------------------------------------- | ----------------------------- |
| 1   | 正規化済みクエリ**全体**の部分一致                          | `のど自慢`、`こ`、`TCUホール` |
| 2   | 全ての語を含む（AND）                                       | `9号館 ダンス`                |
| 3   | いずれかの語を含む（OR）。**一致した語の数**→スコアで並べる | `9号館でやってるダンスのやつ` |

### トークン化の2つの規則

- **1〜2文字の区切り語（助詞など）は、左に2文字以上残せるときだけ切る。**
  この制限が `のど自慢` を守っている
- **3文字以上の区切り語は語頭からでも切る。** `やってるだんす` → `だんす`。
  3文字続けて一致する語が別の単語の一部である確率は低い

### 「の企画」問題

上の規則の副作用で、**語頭の助詞は次の語へ吸着する。** `おすすめの企画を教えて` は
`の企画` という、どの企画にも一致しえない語を作る。`isNoiseToken()` が
「助詞を剥がした残りが不要語」の形をまとめて捨てることで対処している。

**助詞を無条件に剥がしてはいけない**（`のど自慢` が `ど自慢` になる）。
剥がした残りが不要語だったときに限る。

### 検索語が0個のときは全件を返す

`tokenizeQuery()` が空配列を返すのは「0件」ではなく「**絞り込む条件が無い**」という意味。
`searchEvents()` はこの場合に入力をそのまま返す。`おすすめの企画を教えて` で
0件を出すと、検索が壊れているようにしか見えない。

段1が先に走るので、`企画` のように**実際に一致する語**であれば普通にヒットする。
「全件返す」に落ちるのは、literal な一致も意味のある語も無かった場合だけ。

### フィールドの重み

| フィールド                       | 重み |
| -------------------------------- | ---- |
| `title`                          | 5    |
| `organizer` / `place` / 導出建物 | 3    |
| `description`                    | 2    |
| `content`（タグ除去後）          | 1    |

`content` は `stripHtml()` を通す。**タグを残すと `a` や `p` の1文字検索が全件に当たる。**

導出建物を対象に含めているので、`place` が `９号館アリーナ` の企画を `9号館` で引ける。
ただし `その他` は建物名ではなく振り分け先の名前なので、検索対象から外している
（含めると「その他」で検索したときに解決できなかった企画が全部出る）。

## 建物の導出

`resolveBuildingId(place, building)` の解決順。**この順序が仕様。**

1. `building` が入稿されていればそれを使う（`7` のような番号だけの入力も読む）
2. `place` を `buildings` の**宣言順**で部分一致
3. 教室コード規則 `/^([1-9])\d{1,2}[a-z]?$/` — 先頭1桁が号館番号（`11D`→1号館 / `61C`→6号館）
4. どれにも当たらなければ `OTHER_BUILDING_ID`（企画がどこにも属さず消える経路は無い）

> [!IMPORTANT]
> **`buildings` 配列の並び順は仕様である。** 守るべき順序は2つ。
>
> 1. `10号館` を `1号館` より前に置く
> 2. **`号館` 系をすべて `体育館`（`アリーナ`）より前に置く**
>
> 2 を崩すと `９号館アリーナ` が体育館へ倒れ、実データで3件が誤配される。
> `src/data/filter-options.test.ts` の「号館はアリーナより先に判定される」が
> この順序を固定している。

`src/data/stages.ts` の `extractStageId` / `resolveStageId` と同じ形にしてある。
`その他` を `buildings` 配列へ入れていないのも同じ理由で、あの配列は「実在する建物」の
定義であり、「その他」は建物ではなく振り分け先の名前だから。

### 選択肢は実データから作る

`listBuildingOptions(events, selected)`（`src/lib/filters.ts`）が、**企画が1件以上ある建物だけ**を
返す。`src/lib/timetable.ts` の `listStageTabs()` と同じ設計。

**選択中の値は該当0件でもリストへ残す。** 外すと `<select>` の `value` が選択肢に無い状態
になり、**表示が「すべて」へ化けたまま0件が並ぶ。** `parseBuilding()` は
`isKnownBuildingId()` を通った値をそのまま採るので、定義済み14建物のうち実データに企画が
無いもの（2026-09-06 時点で 2〜5 / 7 / 8 / 10号館 / グラウンドの8件）と「その他」は、
`/events?building=7号館` のような深いリンクで普通に踏める。

実測（2026-09-06 / 本番ビルド / 実 Chrome / `?building=7号館`）:

| 状態   | `<select>` の options | `value` | 表示       | 件数 |
| ------ | --------------------- | ------- | ---------- | ---- |
| 修正前 | `7号館` **無し**      | `all`   | 「すべて」 | 0    |
| 修正後 | `7号館` あり          | `7号館` | 「7号館」  | 0    |

修正前の見え方は「絞り込んでいないのに1件も無い」であり、**このPRが潰そうとした
「無言の0件」そのもの**になる。

> [!IMPORTANT]
> **`selected` を渡せるのはクエリを読める場所だけである。** `src/app/events/page.tsx` は
> `useSearchParams()` を読まない設計（#156）なので選択値を知らない。したがって作る場所は
> 2つに分かれる。
>
> | 作る場所                  | 呼び方                                         | 用途                                   |
> | ------------------------- | ---------------------------------------------- | -------------------------------------- |
> | `src/app/events/page.tsx` | `listBuildingOptions(events)`                  | `<Suspense>` の fallback（クエリ無し） |
> | `EventsContent`           | `listBuildingOptions(initialEvents, selected)` | 本描画                                 |
>
> **2箇所で作っても中身はずれない。** fallback は定義上 `building: "all"`（`DEFAULT_EVENT_FILTERS`）
> なので選択値を持たず、差は「選択中の1件」だけ——それがまさに欲しい差である。
> 逆に `page.tsx` の配列を本描画へ降ろすと、`selected` 引数が production から一度も渡らず、
> **`listBuildingOptions` の単体テストだけが緑になる**（#207 のレビューで発覚）。

## URL クエリの検証

`parseEventFilters()` は以前 `as` キャストだけで、`?type=Stage`（大小文字違い）も
`?type=bogus`（存在しない値）も**エラーにも既定値にもならず静かに0件**を返していた。
来場者からは「絞り込みが壊れている」と見える。

現在は `date` / `type` をホワイトリスト照合（`toLowerCase()` 後）、`building` を
`isKnownBuildingId()` で照合し、外れたものは `"all"` へ倒す。`keyword` は `trim()` する
（`?keyword=%20` は truthy なので、trim しないと空白の検索が走る）。

## 日程の `both` は Day1 / Day2 の両方に出す

来場者にとって「両日やっている企画」は「1日目にやっている企画」である。厳密一致にすると
「あるはずの企画が出ない」というバグに見える。

**判定は `matchesEventDate()`（`src/lib/filters.ts`）が1つだけ持つ。**
`src/lib/timetable.ts` の `filterEventsByDate()` もこれを import している。
規則を2箇所に書くと、片方だけ変えたときに企画一覧とタイムテーブルで同じ日の件数が食い違う。

## キーワード入力（`EventFilters`）

- **`router.push` ではなく `router.replace`。** push だと1文字ごとに履歴が積まれ、
  戻るボタンが「1文字ずつ戻る」だけの操作になる（実測: 6文字入力で履歴増加 0 件）
- **300ms のデバウンス**（`KEYWORD_DEBOUNCE_MS`）。URL を直接 `value` にすると、
  ナビゲーションが追いつかない間に入力した文字が巻き戻る。尺は #206 に合わせてある
- **自分が送った値のこだまは無視する**（`lastSentRef`）。`ab` を送った直後に `abc` まで
  打った状態でナビゲーションが完了すると、遅れて届いた `ab` を「外からの変更」と誤認して
  入力欄を巻き戻してしまう

### IME の扱い

**`InputEvent.isComposing` から判定する。** `compositionstart` / `compositionend` と
`input` の発火順はブラウザで揃っておらず、`compositionend` を送信再開の合図にすると
環境によって検索が動かなくなる。`isComposing` は変換中の input には `true`、確定後の
input には `false` が入るので、入力イベントだけで確実に切り替わる。
`onCompositionEnd` は、確定後の input が来ない環境に備えた保険として残してある。

**`onChange` 側は止めない。** 止めると確定した文字が入力欄へ入らない環境が出る。
入力欄は常に追従させ、URL へ送るのだけを待たせる。

実測（2026-09-06 / 本番ビルド / 実 Chrome）:

| 局面            | URL               | 入力欄   | 件数             |
| --------------- | ----------------- | -------- | ---------------- |
| 変換中 `だんs`  | 変わらない        | `だんs`  | 18（全件のまま） |
| 確定後 `だんす` | `?keyword=だんす` | `だんす` | 2                |

> [!WARNING]
> **ハイドレーション完了前にイベントを流すと、この検証は嘘をつく。**
> 2026-09-06 の検証で、`navigate` 直後に合成イベントを流したために
> 「変換確定後も検索が走らない」という**事実と正反対の結果**を3回続けて得た。
> 測る前に「クエリ無し・入力欄が空・全18件」を読み、前提が揃ってから流すこと
> （[browser-verification-pitfalls.md](./browser-verification-pitfalls.md) の系統）。
