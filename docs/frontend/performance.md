## 2026-08-29 Tailwind のソース走査範囲を src/ へ限定

### 背景と仮説

Tailwind v4 の自動ソース検出は「`.gitignore` されていない全ファイル」を走査する。
`docs/**/*.md` や `README.md` のコード例に含まれるクラス名も候補として拾うため、
アプリが一切使っていない規則が本番CSSへ出力されていた。
実例として `.min-h-[60vh]{min-height:60vh}` は、実装から消えたあとも
`docs/frontend/browser-observation-limits.md` の記述だけを根拠に生成され続けていた。

「未使用CSS 97 KiB（PR #105 の計測）の一因ではないか」という仮説を立てて計測した。

### 計測結果 — 仮説はほぼ否定された

`@import "tailwindcss" source(none);` + `@source "../../src";` の前後でビルドを比較した。

| 指標           | 変更前 | 変更後 | 削減            |
| -------------- | ------ | ------ | --------------- |
| 配信CSS raw    | 87,448 | 85,498 | 1,950 B（2.2%） |
| 配信CSS brotli | 12,431 | 12,151 | 280 B（2.3%）   |
| CSS規則数      | 793    | 777    | 16 規則         |

**`docs/` 由来の未使用CSSは brotli で 280 バイトしかない。97 KiB の説明にはならない。**
この変更は性能改善ではなく、「ドキュメントの記述が本番成果物へ漏れない」という
正しさの担保として入れている。性能を根拠に語ってはいけない。

削除された16規則が本当に未使用であることは、変更前後のCSSからセレクタ集合を抽出して
差分を取り、各クラス名が `src/` に存在しないことを機械的に確認した（増えた規則は0件）。

### CSSチャンクの実態

ビルド出力の3つのCSSは役割が異なる。サイズだけを見て判断しないこと。

| チャンク | 実サイズ | 内容                        | 全ルートのHTMLから参照 |
| -------- | -------- | --------------------------- | ---------------------- |
| 本体     | 85 KB    | Tailwind（全ルート共通）    | される                 |
| フォント | 187 KB   | Kaisei Opti の `@font-face` | されない（遅延読込）   |
| LogoLoop | 2.8 KB   | 協賛ロゴ列                  | されない（遅延読込）   |

最大の187 KBはフォントCSSで、既に遅延配信へ切り出し済み（「2026-08-26 フォントCSSの分割・削減」）。
初期表示でブロックするCSSは85 KB（brotli 12 KB）の本体だけである。
Lighthouse の「未使用CSS」は**そのページで使われていない規則**を数えるため、
全ルート共通の単一バンドルを配信する構成では、他ルートぶんの
ユーティリティが常に未使用として計上される。これは死んだCSSではない。

### 副次的に判明したこと

`@utility text-hero-title`（`src/app/globals.css`）は**どのコンポーネントからも使われていなかった**。
`DESIGN.md` に記載があるだけで実装からの参照がなく、走査範囲を絞ると出力されなくなる状態だった。

**消し忘れと判断し、2026-08-29（PR #117）で定義を削除した。** 意匠そのものは `DESIGN.md` の
「Hero タイトルエフェクト」へ未実装の記録として残してあるので、必要になった時点で再定義できる。

なお走査範囲を絞ったことで、**ドキュメントでの言及だけを根拠に `@utility` が
出力され続けることはなくなった**。定義した `@utility` は `src/` で実際に使うこと。

## 2026-08-30 ScrollTrigger を初期チャンクから外す

`data-*` 属性方式の入場モーションを `src/lib/use-scroll-reveal.ts` へ集約した際、
ScrollTrigger の読み込みを **IntersectionObserver 越しの動的 import** へ統一した。

実測（本番ビルドの SSR HTML に、ScrollTrigger 本体を含むチャンク 44K が
`<script>` として載るかどうか）。

| ページ          | 集約前                       | 集約後               |
| --------------- | ---------------------------- | -------------------- |
| `/access`       | **初期スクリプトに含まれる** | 初期スクリプトに無い |
| `/special/[id]` | **初期スクリプトに含まれる** | 初期スクリプトに無い |
| `/events`       | 無い                         | 無い                 |

買っているのは TBT / parse コストであってネットワークではない。IO の root は
下層ページではページ最上位のラッパーになるため読み込み直後に必ず交差し、
往復はむしろ1つ増える。

**reveal 系の ScrollTrigger を新規に足すときは、静的 import せずフック経由にすること。**

## 2026-08-30 初期表示モーションの短縮

オープナーとヒーロー入場が長かったため短縮した。あわせて、調査中に判明した
「意図した演出が一度も動いていなかった」バグを修正した。

### 短縮の内訳

| 対象                   | 変更前           | 変更後              |
| ---------------------- | ---------------- | ------------------- |
| オープナー合計         | 2.40s            | **1.60s**（-33.3%） |
| フェーズ数             | 6（うち空待機2） | **2**               |
| スライドアウト         | 1.20s            | 0.75s               |
| ヒーロー入場の出そろい | 0.94s            | **0.66s**           |
| デスクトップ全完了     | 2.40s            | **1.46s**           |
| セーフティタイムアウト | 6000ms           | 3600ms              |
| ページ側フェイルセーフ | 5000ms           | 2800ms              |

演出は2フェーズに整理した。濃紫背景 + 白ロゴをフェードインして見せ、そのまま
レイヤーが下へ開く。白ロゴからカラーロゴへのクロスフェードは、尺を詰めると認識しづらく
段階として機能しなくなるため廃止した。

**濃紫の上ではカラーロゴ（`favicon.webp`）を使わないこと。** 実物を撮って比較したところ、
淡い配色が背景に沈み、歯車の細部や色の差が判別できなかった。1.6 秒の提示では形として
認識される前に消える。白ロゴ（`favicon-white.webp`）はシルエットが明瞭に立つ。

尺は GSAP に実際にタイムラインを組ませて実測し、`tl.duration()` が 1.6s、
`tl.labels.heroCue` が 0.8s、call の実発火が 799ms、完了が 1599ms であることを
確認している。

### ヒーロー入場が覆いの裏で終わっていた件

`HeroSection` は `document.querySelector("[data-opener-active]")` の有無で
オープナーの在否を判定していたが、**この判定は初回表示で必ず false になる**。

`Opener` は `dynamic(ssr:false)` なので SSR HTML にマーカーが出ない。そして
`HeroSection` の `useEffect` は、`OpenerLoader` の `useSyncExternalStore` が
snapshot 不一致で再レンダー → チャンク取得 → `Opener` がマウント、という流れより
**必ず先**に走る。結果、`opener-done` を待たず t≈0 から入場が始まり、0.94秒後には
紫レイヤーの裏で完成していた。覆いが退いた時点でヒーローは静止画である。

`opener-done` の待機機構も 5000ms のフェイルセーフも、この経路では一度も
仕事をしていなかった。判定を `OpenerLoader` と同一の述語 `willRunOpener()`
（メディアクエリ）に置き換えて解消した。

**同種の判定を書くときは DOM マーカーを使わないこと。** マウント順序に依存し、
しかも「動いていない」ことが視覚的に分かりにくい。

### `opener-done` の取りこぼし対策

正しく待つようにすると、今度は**合図を取りこぼす**経路が現れる。`opener-done` は
ワンショットのイベントで、リスナー登録より前に飛ぶと永久に失われるためである。

オープナーは `<body>` 直下にあるのですぐ動き出すが、`{children}` 側はデータ取得を
挟んだストリーミングの後にハイドレートされる。本番ビルドの実測で、オープナーの
エフェクトが 1243ms、ヒーローのそれが 2773ms と **1.5秒の開き**があった。ハイドレーションが
さらに遅れる環境（他のプロセスが重い、低速端末）では、合図が先に飛んで
ヒーローが `opacity: 0` のまま取り残される。

`src/lib/motion.ts` の `markOpenerDone()` / `hasOpenerFinished()` で、発火済みかを
`window` のフラグに記録して解消した。リスナーを張る前に必ずこれを確認する。

```ts
const shouldWaitForOpener = willRunOpener() && !hasOpenerFinished();
```

フラグをモジュールスコープの変数ではなく `window` に置くのは、`motion.ts` が
初期チャンクと遅延チャンクの両方から参照され、バンドラがインライン複製すると
別インスタンスになりうるため。**発火とフラグ設定は必ず対で書くこと**
（`Opener.tsx` の3箇所すべて: 通常の合図・セーフティタイムアウト・モバイル即時完了）。

### 削除したもの

- pulse アニメーション: `scale:1.04 / duration:1.5 / yoyo` が 0.3s 地点で開始し
  1.1s 地点で kill されるため目標値に到達せず、実測で視認できなかった
- `LogoVideo.tsx` と `logo-animation.webm` / `.mp4`（計約933KB）: どこからも
  参照されていない孤児。動画は実測4.87秒のうち末尾0.8秒が完全な静止だった
- `@utility animate-spin-slow`（240s）: 同名の `@layer utilities` 版（60s）が
  勝っており、ビルド済みCSSに240sは一切出力されていなかった

## 実装ルール

### LCP 要素

- LCP 候補はサーバーHTMLから可視状態にする。
- オープナーや入場演出の完了を LCP 表示条件にしない。
- `next/image` の `sizes` は実際のブレークポイント別表示幅に合わせる。
- ファーストビューの LCP 画像には高優先度を明示する。

### 動画とアニメーション

- ヘッダーの常設ロゴに動画を自動読み込みしない。ブランド演出はオープナーへ集約する。
- スクロール連動の補間は `transform` / `opacity` を使い、`width` をアニメーションしない。
- オープナーは `window.load` を待たず、ハイドレーション後に開始する。
- 初期表示モーションの尺は `src/lib/motion.ts` に集約する。オープナーの合計は
  LCP を覆う時間の上限なので、コンポーネント内に散らさない。
- タイムライン内の位置は `tl.duration()` からの逆算ではなく `addLabel` で表す。
  逆算はフェーズの尺を変えた瞬間に意味が壊れ、しかも壊れたことに気づけない。
- 演出が「オープナーの完了を待つ」判定に DOM のマーカーを使わない。Opener は
  `dynamic(ssr:false)` なので、各ページの `useEffect` より後にしかマウントされない。

### 画像

- ローカル画像と許可済みリモート画像は原則 `next/image` を使う。
- 固定表示サイズでも `width` / `height` / `sizes` を明示する。
- microCMS の画像を原寸のままロゴ一覧へ渡さず、表示寸法に応じて最適化する。

### 無限ロゴ列

- `aria-hidden="true"` の複製列にはリンクやボタンを置かない。
- キーボード・支援技術で操作可能なのはアクセシビリティツリーに残す先頭列だけとする。
- ポインター操作は、複製列から非フォーカス要素を通じて先頭列と同じ処理へ委譲してよい。
- 複製画像の `alt` は空にする。

### Webフォント

- `next/font` の変数をルート要素へ付けると、対応するフォントCSSが全ページへ配信される。
- 初期表示に不要な装飾フォントは、遅延チャンクで変数を付け、初期HTMLのrender-blocking CSSに含めない。
- 使用箇所のないフォントは import・変数・CSS utility を残さない。
- 日本語フォントは `unicode-range` ごとの分割ファイルが多いため、原則 `preload: false` とし、
  実際に使う文字範囲だけをブラウザに取得させる。
- 複数ウェイトを使う可変フォントは、静的ウェイトを列挙せず variable font を優先する。
- ブランド上必要なフォントでも、使用ウェイトと preload 対象を最小限にする。
- **文字数が固定の見出しは、その文字だけのサブセットを自前配信する。** ヒーローの
  「第97回世田谷祭」8文字は `public/fonts/dela-gothic-one-hero-400.woff2`（1,876バイト）
  として持ち、`@font-face` を `globals.css` に直接書く。`next/font` で日本語フォントを読むと
  `@font-face` 数百面 / CSS 数十 KB のチャンクが増えるため、2桁の差が出る。
  サブセットは Google Fonts の `&text=` で生成できる（手順は `globals.css` のコメント）。
  **`unicode-range` を文字に固定するため、文言を変えたら woff2 を作り直すこと。**
- **`&text=` が効かないファミリーがある。** `Noto Sans JP` は `text=` を指定しても可変フォント
  全体（2.2 MB）を返す。サブセット前提の書体選定では、取得後に必ずファイルサイズを確認する。
- **端末標準フォントで代替しない。** `Hiragino Kaku Gothic ProN` などは macOS / iOS にしか
  無く、Windows と Android では全く別の書体になる。ブランド要素には使わない。

## 検証

1. `pnpm lint`、`pnpm format:check`、`pnpm build` を通す。
2. ローカル本番ビルドを desktop / mobile で表示し、画像寸法・横スクロール・操作性を確認する。
3. `visibilityState` と `framesIn1s` を記録してから、オープナーとスクロール演出を確認する。
4. Lighthouse を同条件で複数回実行し、中央値を比較する。
5. 本番反映後は PageSpeed Insights で LCP 内訳、画像削減量、アクセシビリティ監査を再確認する。

## 2026-08-26 フォントCSSの分割・削減

PR #106 の本番 mobile 計測では、初期HTMLのCSSリンクは3本に減った一方、遅延後に読み込まれる
フォントCSSが未使用CSSとして約97 KiB残った。ブラウザ実測で `font-sans` はシステムフォントへ
解決しており、Noto Sans JP の `@font-face`（転送約31 KiB）は使用されていなかった。

本PRでは次を行う。

- 未使用だった Noto Sans JP の `next/font` import と変数を削除し、`font-sans` を明示的なシステム
  フォントスタックへ戻す。
- Dela Gothic One はホームの `HeroSection` だけで遅延ロードし、他ページへCSSを配信しない。
- Kaisei Opti はホームの初期ビューポートでは読み込まず、非ホームではハイドレーション後、ホームでは
  ABOUT / NEWS がビューポートへ近づいた時点で一度だけ読み込む。

これによりホーム初期表示からNoto Sans JPとKaisei OptiのフォントCSSを外し、ブランド見出しは
対象ページ・対象セクションで適用する。初期の見た目をシステムフォントで崩さないこと、ABOUT / NEWS
のスクロール演出とフォント適用が競合しないことをブラウザで確認する。

## 2026-08-26 残存CSS・JS・render-blocking・画像の対応

PR #107 の本番 mobile 計測（Performance 92、FCP 1.4 秒、LCP 2.9 秒、TBT 10 ms、CLS 0）では、
次の残存候補を確認した。

- 未使用CSS: 推定 31 KiB。Dela Gothic One のフォントCSS（約32 KiB）がほぼ全量未使用。
- 未使用JavaScript: 推定 22 KiB。初期チャンクに含まれる下部セクション・演出用コードが対象。
- render-blocking: 推定 170 ms。LogoLoop CSSを含む初期スタイルシートが対象。
- 画像配信: 推定 27 KiB。ヒーロー画像・ヘッダーロゴ・フッターロゴの圧縮余地。

次回の性能改善PRでは、以下の方針で対応する。

- ホームのヒーロー文字を端末標準の丸ゴシックへ切り替え、使用箇所のないDela Gothic Oneの
  `next/font` import・遅延ローダー・CSS utilityを削除する。
- オープナー、ABOUT、企画カルーセル、スポンサーのLogoLoopを動的ロードへ分離する。スポンサー欄は
  静的ロゴと高さをSSRし、IntersectionObserverで近接時だけ `ssr: false` のLogoLoopを読み込むことで、
  CSS/アニメーションJSを初期HTMLから外しつつ、遅延・失敗時もロゴ表示とレイアウトを保つ。
- `next/image` のAVIFを優先形式へ追加し、既存WebPを未対応ブラウザ向けフォールバックとして残す。
  ヘッダー・フッターの固定ロゴは品質を75から60へ下げ、表示寸法に対して過剰な転送を避ける。

下部セクションの見出しと本文はSSRを維持し、データ欠落時のレイアウトとSEOを変えない。今回の検証は
ローカル本番ビルドと静的HTMLの参照確認までとし、マージ・本番反映後に同一URL・mobile presetで
PageSpeed Insightsを再計測して、未使用CSS/JS、render-blocking、画像削減量を比較する。

## 2026-08-27 残存JavaScript・先読み・初期タスクの対応

PR #110 の本番 mobile 計測（Performance 98、FCP 0.9 秒、LCP 2.4 秒、TBT 0 ms、CLS 0）で、
未使用JavaScript約22 KiB、render-blocking約110 ms、長時間タスク1件が残った。実機相当ブラウザの
ネットワーク記録では、初期表示直後にモバイルメニュー・オープナーの演出チャンクと、表示中リンクから
複数ページの先読みチャンクが取得されていた。

次の性能改善PRでは、初期ビューポートで不要なJavaScriptと先読みを抑える。

- モバイルではオープナー本体（GSAPを含む）を読み込まず、デスクトップかつモーション軽減なしの場合だけ
  ハイドレーション後にロードする。空の `opener-container` で初期レイアウトを保つ。
- モバイルメニューは開く操作またはフォーカス・ポインター接近時まで本体チャンクを取得しない。
- ヘッダーとヒーローの初期表示リンクでは Next.js の自動 route prefetch を無効化し、ユーザー操作時の
  遷移は維持する。

ローカル本番ビルドの 390x844 では、初期4秒間にモバイルメニュー・オープナー・ページ先読みの追加チャンクが
発生しないこと、メニュー操作後にのみメニューチャンクが取得され操作できることを確認する。モバイルの
PageSpeed Insights は本番反映後に再計測し、未使用JavaScript・render-blocking・長時間タスクを比較する。
