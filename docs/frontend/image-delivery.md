# 画像配信の経路

画像の変換を **どこにやらせるか** を決めているドキュメント。
Lighthouse 基準値や個別の最適化手法は [`performance.md`](./performance.md) を参照。

## 結論から

**変換は2つとも Vercel の外でやる。Vercel の変換枠の消費は 0 にする。**

| 画像の出どころ                          | 変換する場所                                       | 枚数 | Vercel の変換数 |
| --------------------------------------- | -------------------------------------------------- | ---- | --------------- |
| microCMS（`images.microcms-assets.io`） | imgix（microCMS の配信）・実行時                   | 93+  | **0**           |
| `public/` 配下の静的画像                | **手元で事前に AVIF 化**（`pnpm images:optimize`） | 11   | **0**           |

**枠は総量で枯れる。** #240 では「静的画像は枠 5,000 の 7% しか使わないので Vercel に
残してよい」と判断したが、**すでに枯れた枠の上では消費の少なさは何も保護しない。**
実際 2026-09-20 にはトップページの静的画像 srcset 128通り中81通りが 402 で、
オープナーのロゴは Retina で必ず消えていた（#241。「静的画像を Vercel から外した理由」を参照）。

すべての画像は [`src/components/ui/AppImage.tsx`](../../src/components/ui/AppImage.tsx) の
`AppImage` で描く。出どころの判定は実行時に `src` を見て行うため、呼び出し側が区別する
必要は無い。

> [!IMPORTANT]
> **`next/image` を直接 import してはいけない。** `eslint.config.mjs` の
> `no-restricted-imports` が error で止める（例外は `AppImage.tsx` のみ）。

## なぜこうなったか（#237）

2026-09-19、本番の企画サムネイルが一部だけ表示されなくなった。原因は
**Vercel Free Plan の変換枠（Hobby は月5,000変換）の枯渇**である。

```
$ curl -sI 'https://setagayafes.org/_next/image?url=<microCMS画像>&w=384&q=75'
HTTP/2 402
x-vercel-error: OPTIMIZED_IMAGE_REQUEST_PAYMENT_REQUIRED
```

### 「一部だけ」になる理由を理解しておくこと

課金単位は画像1枚ではなく **変換1回**、すなわち `(元画像, 幅, 品質, フォーマット)` の
組み合わせ1つである。そして変換済みの結果は CDN に残る。したがって枯渇後はこうなる。

- 枯渇**前**に変換済み → CDN から `200` で配信され、いまも表示される
- 未変換の組み合わせ → `402` で壊れる

同一ファイルでも幅で生死が分かれる。`favicon-outline.webp` の実測。

```
200  w=320 / 384 / 420 / 512 / 640 / 750 / 1080
402  w=256 / 1200 / 1920 / 2048 / 3840
```

**画面幅と DPR で表示される画像が入れ替わるため、「ときどき一部が壊れる」という
再現しにくい形で表面化する。** 枯渇を疑う前に画像やコードを探すと何も見つからない。
**`x-vercel-error` ヘッダを最初に見ること。**

### 何が枠を食っていたか

`sizes` に固定 px を書いても、srcset には `deviceSizes` + `imageSizes` の**全候補**が並ぶ。
当時は18本あった。これに AVIF / WebP の2フォーマットが掛かる。
microCMS の企画サムネイルだけで93枚あり、News と協賛ロゴが上乗せされていた。

## imgix 側のパラメータ

`AppImage` が microCMS の画像へ付けるのは `w` / `q` / `fm=avif` / `auto=compress` /
`fit=max` の5つ。いずれも実測で決めている。

### `auto=format` は使えない

imgix の `auto=format` は Accept ヘッダを見て AVIF / WebP を出し分ける機能だが、
**microCMS の前段にある CloudFront が Accept を転送しないため機能しない。**
`Accept: image/avif,image/webp,...` を明示しても応答は `image/jpeg` のままで、
`Vary` ヘッダも返らなかった。

| 指定                         | 応答         | サイズ  |
| ---------------------------- | ------------ | ------- |
| `auto=format`（Accept 明示） | `image/jpeg` | 15,772B |
| `fm=webp&q=75`               | `image/webp` | 11,170B |
| `fm=webp&q=75&auto=compress` | `image/webp` | 8,506B  |
| `fm=avif&q=75&auto=compress` | `image/avif` | 5,651B  |

出し分けができない以上フォーマットは固定するしかない。**AVIF を選んでいる。**

### AVIF を選んだ根拠（2026-09-20 実測）

公開中の入稿画像30本（4ルート×2画面幅でブラウザが実際に取得したもの）を両形式で取り直した。

| 対象                        |        WebP |      AVIF |  削減 |
| --------------------------- | ----------: | --------: | ----: |
| 全30本                      | 1,568,048 B | 996,780 B | 36.4% |
| `/`（mobile）               |   215,776 B | 133,254 B | 38.2% |
| `/special`（mobile）        |   246,198 B | 149,855 B | 39.1% |
| `/about/sponsors`（mobile） |    70,262 B |  50,469 B | 28.2% |
| `/events`（mobile）         |   163,418 B | 121,145 B | 25.9% |

**30本すべてが `image/avif` を返した**（失敗0件）。元形式は jpg / jpeg / png / webp で、
GIF（アニメーション）は1本も無い。現在の入稿画像に透過も無い（`hasAlpha=false`）。

#### フォールバックを捨ててよい理由は4つある

1. **サポート下限がすでに AVIF を要求している。** 下限（iOS Safari 16.4 / Chrome 111 /
   Firefox 128）は TailwindCSS v4 の `@property` / `color-mix()` 由来で、AVIF の下限
   （Safari 16.0 / Chrome 85 / Firefox 93）より高い。
   **AVIF が読めない環境では、そもそも CSS が効かずレイアウトが崩れている。**
2. **本番はすでに全画像を AVIF で配っている。** `next.config.ts` の `formats` は #107 から
   AVIF 優先で、実測でも本番は `content-type: image/avif` を返す。PR #110 の
   Lighthouse 基準（Performance 98 / LCP 2.4秒）も AVIF 配信下で取った値である。
   **AVIF は新しいリスクではなく現状。**
3. **OGP は影響を受けない。** [`src/lib/metadata.ts`](../../src/lib/metadata.ts) は
   `thumbnail.url` から `w=1200&h=630&fit=fill&fill=solid&fill-color=…` を独自に組み立てており
   **`fm=` を付けない。** AVIF 非対応のクローラ（X など）には原形式（PNG / JPEG）が届く。
4. **デコードは重くならない。** 下の実測を参照。

#### デコード実測（低性能Android相当・CPU 6x）

`createImageBitmap` の所要時間のみ（7回の中央値）。

| 画像              | 幅   | WebP              | AVIF              | 差         |
| ----------------- | ---- | ----------------- | ----------------- | ---------- |
| `S__26755118.jpg` | 828  | 104,462B / 9.4ms  | 65,028B / 10.7ms  | **+1.3ms** |
| 同                | 1080 | 173,074B / 15.1ms | 104,854B / 11.3ms | −3.8ms     |
| 同                | 1920 | 249,388B / 22.7ms | 160,245B / 13.5ms | −9.2ms     |
| `UPBEAT.png`      | 828  | 11,634B / 3.2ms   | 6,808B / 4.1ms    | +0.9ms     |
| 同                | 1920 | 22,614B / 5.9ms   | 10,818B / 4.5ms   | −1.4ms     |

**悪化は最大 +1.3ms。** 幅が大きいほど AVIF のほうが速い（デコードするデータ量が少ないため）。
`/events` を Slow 4G + CPU 6x + 無限スクロール完走で通したページ計測でも、
転送 36,564B → 28,229B に対し **LCP は 1,444ms → 1,440ms で差が出なかった**（5回の中央値）。

> [!NOTE]
> 残るリスクは、企業プロキシの再エンコードのような**想定外の環境**だけである。
> 切り戻すときは [`src/lib/image-loader.ts`](../../src/lib/image-loader.ts) の `fm` と
> [`src/lib/image-loader.test.ts`](../../src/lib/image-loader.test.ts) の期待値、
> そしてこの節を同じコミットで戻すこと。

### `fit=max` は必須

imgix は既定で**拡大もする**。入稿画像の寸法は入稿者任せで、`deviceSizes` の上端（3840）に
届かないものが大半である。

| 指定                  | 実寸      | サイズ  |
| --------------------- | --------- | ------- |
| `w=1920&fm=webp&q=75` | 1920x1920 | 65,952B |
| 同上 + `fit=max`      | 1081x1081 | 35,886B |

`fit=max` が無いと、劣化した水増し画像を倍近い転送量で配ることになる。
（上表は `fm=avif` へ切り替える前の実測で、取得は `fm=webp`。倍率の話なので結論は変わらない。）

## 静的画像を Vercel から外した理由

2026-09-20 に本番HTML（13ルート）の srcset を全数えした結果が次である。
`formats` が2つなので、変換数の上限は通り数の2倍。**この計測自体は正しい。**

| 出どころ                           | srcset の組み合わせ | ×2形式 = 上限 | 枠 5,000 に対して |
| ---------------------------------- | ------------------: | ------------: | ----------------: |
| `public/` の静的画像（11ファイル） |            178 通り |       **356** |            **7%** |
| microCMS（この13ページ分だけで）   |            386 通り |           772 |                 — |

microCMS の実際の総量はこれでは済まない。企画サムネイルだけで93枚あり、旧設定の18幅×2形式で
**約3,348変換**。News と協賛ロゴが上乗せされる（#237）。

> [!CAUTION]
> **ここから「だから静的画像は Vercel に残してよい」と結論したのが #240 の誤りである。**
>
> 枠は**アカウント全体の総量**で枯れる。消費が 7% の利用者も、枯れた枠の上では
> 未変換の組み合わせがすべて 402 になる。**変換数の少なさは保護にならない。**
> しかも枠は直近30日のローリング窓なので、一度枯れると約1か月戻らない。
>
> 2026-09-20 の実測: トップページの静的画像 srcset **128通りのうち81通り（63%）が 402。**
> ファイル別の生存幅は次のとおりで、**ビューポートと DPR の組み合わせ次第でどれも壊れうる。**
>
> | ファイル                       | 品質 | 200 を返す幅                         |
> | ------------------------------ | ---- | ------------------------------------ |
> | `favicon-outline.webp`         | 40   | 384 / 420 / 640 / 750 / 828 / 1080   |
> | `favicon-white.webp`（Opener） | 60   | **256 / 384 のみ**                   |
> | `logo.webp`                    | 60   | 256 / 420 / 640                      |
> | `logo-white.webp`              | 60   | 48 / 64 / 96 / 128 / 256 / 384 / 640 |
> | `tcu-7.webp`                   | 75   | 640 / 750 / 828 / 1080 / 1200        |
> | `mon7a.webp`                   | 75   | 384 / 420 / 640 / 750 / 828 / 1080   |
> | `mon7a-logo.webp`              | 75   | 256 / 384 / 640 / 750                |
> | `setagayafe97-image.webp`      | 75   | 384 以上すべて                       |
> | `geer1.webp`                   | 75   | 64 / 96 / 128 / 256                  |
> | `geers.webp`                   | 75   | 256 / 384                            |

### オープナーのロゴは巡回で捉えられなかった

下の「実ブラウザで数えた」検証は **9ルート×2画面幅**で回したが、
**`favicon-white.webp` を一度も捉えていない。**

`Opener` は `dynamic(ssr: false)` で、**デスクトップ幅かつ
`prefers-reduced-motion: no-preference` のときだけ 1.6 秒間だけ DOM に存在**し、
その後 unmount される。レイアウト撮影で `prefers-reduced-motion: reduce` を立てる運用とは
そもそも噛み合わない。#241 の「原寸配信になった静的画像9種」の表にも入っていない。
**この画像は2度、調査から漏れた。**

`sizes="256px"` には `vw` が無いため `getWidths` は `widths: allSizes` へ落ち、
**16幅すべてが srcset に並ぶ**。DPR2 のブラウザは w=640 を選び、それは未変換だった。

> [!IMPORTANT]
> **短時間しか DOM に無い画像・条件付きでしか描かれない画像は、巡回では数えられない。**
> 数え漏らしを設計の根拠にしないこと。`unoptimized` へ移したことで、この検出漏れの
> 階級そのものが消えた（実体が1つしか無いので「どの組み合わせが未変換か」が存在しない）。

### 「静的画像も全部 402 だった」は測り方の誤りだった

当初は静的画像も `unoptimized` にする設計だったが、その根拠にした Preview の実測は
**`curl` に `Accept` ヘッダを付けずに叩いた結果**だった。ブラウザが決して要求しない
形式変種を尋ねているので、キャッシュ済みでも 402 になる。2026-09-20 に付け直した。

| URL                        | Accept なし | Accept あり              |
| -------------------------- | ----------- | ------------------------ |
| `logo.webp` `w=640&q=60`   | 402         | **200 / 14,965B / avif** |
| `tcu-7.webp` `w=828&q=75`  | 402         | **200 / 43,181B / avif** |
| `tcu-7.webp` `w=1080&q=75` | 402         | **200 / 67,233B / avif** |

> [!IMPORTANT]
> **`/_next/image` を `curl` で検証するときは必ず `Accept` を付けること。**
> `Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8`
> 付けないと Vercel は別の形式変種を探しにいき、キャッシュ済みの画像まで 402 に見える。
> より確実なのは実ブラウザで巡回して「**実際に要求された組み合わせ**」だけを数えることである。

実ブラウザ（9ルート×2画面幅）で数えた結果、静的画像は **25通り中 23 が 200、402 は2件だけ**
（どちらもファーストビュー外の `w=750`）。一方 microCMS は 30通り中 8件が 402 だった。

> [!CAUTION]
> **この「25通り中23が200」は 2026-09-20 に覆った。** 巡回が捉えた組み合わせが少なすぎた。
> srcset の候補を全数えすると **128通り中81通りが 402** で、そこにはオープナーのロゴが
> 含まれていない（上の「オープナーのロゴは巡回で捉えられなかった」）。
> **`Accept` を付けて実測する**という教訓は正しいが、**巡回で数えた母数が
> 全体だと思ってはいけない。**

### 事前最適化していない原画像を原寸配信した場合（2026-09-20 実測）

静的画像まで `unoptimized` にし、**原画像をそのまま配った**ときのトップページ
（390×844・DPR2）。#240 が差し戻しの根拠にした数字である。

| 画像                                   | Vercel 経由 |    原寸配信 |      倍率 |
| -------------------------------------- | ----------: | ----------: | --------: |
| `tcu-7.webp`                           |      43,181 |     202,386 |     4.69× |
| `mon7a.webp`                           |      24,105 |     136,784 |     5.67× |
| **`favicon-outline.webp`（LCP 要素）** |  **16,272** |  **76,520** | **4.70×** |
| `setagayafe97-image.webp`              |      12,878 |      53,118 |     4.12× |
| `logo.webp`（ヘッダー）                |       9,021 |      51,520 |     5.71× |
| **合計（8枚）**                        | **139,856** | **653,780** | **4.67×** |

`favicon-outline.webp` は [`performance.md`](./performance.md) がトップの LCP 要素と
名指ししている画像で、`<link rel="preload" fetchPriority="high">` 付きで最優先に取りに行く。

### 事前最適化すれば、その代償は消える（2026-09-20 実測）

**4.67 倍は「Vercel から外したこと」の代償ではなく、「原画像を事前最適化していなかったこと」
の帰結だった。** `assets/source/` の原画像を表示寸法の AVIF へ焼くとこうなる。

| `mon7a`                           |     136,784 |      27,062 |     80% | 920x920   |
| **`favicon-outline`（LCP 要素）** |      76,520 |  **27,350** |     64% | 500x500   |

| `setagayafe97-image`              |      53,118 |      23,555 |     56% | 1024x1024 |
| `logo`                            |      51,520 |      11,588 |     78% | 415x166   |
| **`favicon-white`（Opener）**     |      29,862 |   **9,232** |     69% | 500x500   |
| `geers`                           |      28,184 |      10,976 |     61% | 384x384   |
| `geer1`                           |      19,694 |       3,681 |     81% | 192x192   |
| `mon7a-logo`                      |       9,296 |       2,596 |     72% | 719x191   |

ファーストビュー8枚の合計は **176,719 B**。Vercel 経由の実測 139,856 B に対して **+26%** で、
原寸配信の 653,780 B（+367%）とは比べるまでもない。**1ファイル1寸法になるぶん画面幅ごとの
最適化は失うが、払える額である。** 予算は `scripts/static-image-manifest.mjs` の
`FIRST_VIEW_BUDGET_BYTES`（200,000 B）で、`pnpm check:images` が守る。

品質は**原画との RMSE を測って**決めた（0-255 スケール、`box` へ縮めた原画と復号結果の差）。
ロゴ・線画は `chromaSubsampling: "4:4:4"`（`4:2:0` だと彩度の高い輪郭が滲んで読めなくなる）、
写真は `4:2:0`。

| 画像              | 採用 q | RMSE |
| ----------------- | -----: | ---: |
| `favicon-outline` |     40 | 5.08 |
| `favicon-white`   |     50 | 0.91 |
| `logo`            |     50 | 3.39 |
| `tcu-7`           |     30 | 8.81 |
| `mon7a`           |     50 | 3.40 |

`tcu-7` の RMSE 8.81 は大きいが、**Vercel が配っていた w=1080 / 67,233 B とほぼ同じ
バイト数**（69,911 B）であり、本番で見えていた品質と同等である。手前に clip-path の
リビール演出と本文が乗る背景写真なので、ここに品質を払わない。

### 最適化キャッシュはデプロイをまたいで共有される

同じローカル画像の同じ幅を、本番と過去2つの Preview デプロイで叩くと、いずれも
`200 / 16,272B / image/avif` が返る（`age: 141119` = 39.2時間、`x-vercel-cache: HIT`）。
**デプロイのたびに変換し直す隠れコストは無い。**

### 枠の状態（2026-09-20 時点）

Vercel ダッシュボード（Hobby / All Projects / Last 30 Days）の実測。

| 指標                                     |                使用量 |
| ---------------------------------------- | --------------------: |
| **Image Optimization - Transformations** | **5.1K / 5K**（超過） |
| Image Optimization - Cache Reads         |            57K / 300K |
| Image Optimization - Cache Writes        |            29K / 100K |
| Fast Data Transfer                       |        10.7GB / 100GB |

**Hobby には請求サイクルが無く、集計は直近30日のローリング窓である**
（表示が `Aug 21, 3am - Sep 20` → 1時間後に `4am -` へ動くことで確認。支払い方法も未登録）。
つまり「◯日にリセット」という一点は存在せず、9/19〜9/20 に積んだ分が
**30日後（2026-10-19〜20 ごろ）に窓から抜ける**。それまでは未変換の組み合わせが 402 になる。
microCMS を外した後の新規消費は上限でも月356なので、窓が進めば自然に 5K を下回る。

## なぜ `AppImage` というラッパーなのか

適用方式は2つ試して、いずれも実測で否定している。

| 方式                                        | 結果                                                                                                                                                                                                                                                                                          |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `next.config.ts` の `loaderFile` で全体適用 | **不可。** `images.loader: "custom"` は `/_next/image` を 404 にする（`dev` / `start` 双方で実測。外すと同じURLが 200）。静的画像も Vercel から外したいま巻き添えは起きないが、`loaderFile` は**すべての画像にこのローダーを通す**ため、「どこで変換するか」の決定が `AppImage` と2箇所に散る |
| `<Image loader={fn}>` に関数を直接渡す      | **不可。** Server Component からの受け渡しは prerender 時に `Functions cannot be passed directly to Client Components` で落ちる（`/about/sponsors` で実測）                                                                                                                                   |

`AppImage` が `"use client"` を持つことで、呼び出し側は Server / Client を問わなくなる。
**この失敗は開発サーバーでは顕在化せず、`next build` で初めて出る。**

## 幅の候補（`deviceSizes` / `imageSizes`）

**いまはこの2つは imgix 経路にしか効かない。** `getImgProps` は `loader` の種類に関係なく
ここから幅を決め、その幅をローダーへ渡すが、**`unoptimized` の画像には srcset が出ない**ため
`public/` の静的画像は影響を受けない。**ここへ幅を1つ足すと microCMS の imgix URL の本数が
増える**（imgix に変換数の課金は無いので枠は焼かないが、HTML は太る）。
追加時は用途を PR に書くこと。

#237 で 512（`deviceSizes`）と 320（`imageSizes`）を落とした。隣接する 640 / 384 との差が
小さく、丸め先との差はそれぞれ 25% / 20% にとどまるため。2048 と 3840 は残している。
head のビルド成果物に出ている imgix URL の幅が、この16値ちょうど（512 / 320 は0本）に
なっていることで効いていることを確認できる。

## 再発防止装置は5つあり、射程が違う

| 装置                                                        | 走る場所            | 守るもの                                                      |
| ----------------------------------------------------------- | ------------------- | ------------------------------------------------------------- |
| `eslint.config.mjs` の `no-restricted-imports`              | `pnpm lint`         | `next/image` の直接 import と**画像の静的 import**            |
| `AppImage` の `Omit<ImageProps, "loader" \| "unoptimized">` | `pnpm type-check`   | 呼び出し側が**個別に最適化へ戻すこと**                        |
| `src/lib/image-loader.test.ts`                              | `pnpm test`         | ローダー関数の契約と**振り分けそのもの**（`resolveDelivery`） |
| `scripts/assert-static-image-budget.mjs`                    | `pnpm check:images` | `public/` の**実体**（役割・形式・寸法・予算・参照の解決）    |
| `scripts/assert-no-image-optimizer.mjs`                     | `pnpm build` の末尾 | **生成物**に `/_next/image` が1本も無いこと                   |

**ユニットテストだけでは足りない。** `AppImage` から `loader` / `unoptimized` の指定が
外れても、ローダー関数は無傷なのでテストは緑のまま素通りする。ビルドは通り、枠が
残っているうちは画面も正常に見える。生成物を読む以外に判定する方法が無い。

ビルド末尾のガードは事前描画された全HTMLを走査し、**出どころを問わず** `/_next/image?url=` へ
画像を渡すURLが1本も無いことを検査する。あわせて **`public/` の静的画像が実体のパスで
出ていること**も見る（0本なら `AppImage` から `unoptimized` が外れた合図で、検査の空振りでもある）。

`pnpm check:images` は別の層を守る。**配信するバイトがリポジトリの中身そのものになった**ので、
役割（OGP や favicon を AVIF 化していないか）・形式・寸法・バイト予算・参照の解決を検査する。
とくに **`.webp → .avif` の張り替え漏れはビルドも lint も型検査も通り、本番で 404 になる。
これを拾えるのはこの検査だけである。**

この検査は manifest を信じない。`src/data/site.ts` の `ogImage` / `searchThumbnail`、
`src/app/layout.tsx` の `icons`、`src/lib/structured-data.ts` の `absoluteSiteUrl(...)`、
`src/lib/sitemap-entries.ts`、`poster=` を**実際に読んで**、そこから参照されているパスが
`role: "app"` になっていたら落とす。「OGP を AVIF 化してしまった」を、manifest の
書き漏らしではなく**シンクの実物**から検出するためである。

### 検証の記録（2026-09-19）

- 正常時: `OK`。生成物の `/_next/image` は **0件**、imgix URL は 1,514 種
- HTML へローカル画像の `/_next/image` を1本注入 → **検出して exit 1**
- `Header.tsx` で `next/image` を直接 import → **ESLint が error で停止**
- ローカル本番サーバーで主要6ページの画像を取得 → **54枚すべて 200**

### ガードが空振りする条件

microCMS の画像が1枚もHTMLに出ないと、検査対象が消える。その場合ガードは `NOTE:` を出して
成功扱いにする（入稿0件や取得失敗と区別が付かないため合否条件にしない）。

> [!IMPORTANT]
> **公開フラグが全て false でも空振りしない。** 協賛企業（`SponsorBanner` と
> `/about/sponsors`）は `NEXT_PUBLIC_*_VISIBLE` のどれにも依存せず、常に microCMS を読む。
> したがって `NOTE` が出るのは「協賛の取得が0件だった」ときであり、**それは正常ではなく
> 異常の合図である。** ログに `NOTE` が出ているときは、検査が効いていないと考えること。

## 残っている制約

- **枠は直近30日のローリング窓**なので「リセット日」は無い。9/19〜9/20 に積んだ分は
  2026-10-19〜20 ごろに窓から抜ける。それまでは未変換の組み合わせが 402 になる
  （実測では静的画像 25通り中2件だけ、どちらもファーストビュー外）
- ~~本対応後の Vercel 変換は静的画像だけで、上限でも月356（枠の7%）。二度と枯れない~~
  **この記述は誤りだった（2026-09-20 に訂正）。** 枯渇済みの枠を考慮していない。
  消費が少ないことは、すでに枯れた枠の上では何も保護しない。恒久対策は消費を減らすことではなく
  **0 にすること**である。いまは Vercel の変換を1回も使わない
- imgix 側には変換数の課金が無く、配信も microCMS の CDN から出る。
  つまり **Vercel の帯域（100GB/月）も消費しない**
- 静的画像の事前縮小は完了（#241）。目標寸法・品質・バイト予算の一次定義は
  `scripts/static-image-manifest.mjs`、焼くのは `pnpm images:optimize`、
  守るのは `pnpm check:images`
- **`public/` の静的画像は AVIF 単独配信で、WebP のフォールバックが無い。**
  下の「静的画像を AVIF 単独で配る判断」を参照
- **切り戻しは枠が回復してからでないと意味が無い。** `unoptimized` を外した先は
  2026-10-19〜20 ごろまで 402 のままである

## 静的画像を AVIF 単独で配る判断

microCMS 側で AVIF 固定を選んだ4つの根拠のうち、**静的画像へそのまま転移するのは
1・4 だけである。2 は転移しない。そこを曖昧にしない。**

| #   | microCMS 側の根拠                      | 静的画像へ転移するか                                                                                                                           |
| --- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | サポート下限が AVIF の下限より高い     | **転移する。** 画像の出どころではなくサイトの CSS（Tailwind v4 の `@property` / `color-mix()`）の性質                                          |
| 2   | 本番はすでに全画像を AVIF で配っている | **転移しない。** `formats` は Accept を見て**未対応ブラウザへ WebP を返していた**。`unoptimized` にするとそのフォールバックが消える            |
| 3   | OGP は影響を受けない                   | **自動では転移しない。** 静的画像は実体ファイルなので、変換対象に入れた瞬間に OGP が AVIF になる。manifest の `role` と逆引き検査が前提条件    |
| 4   | デコードは重くならない                 | **おおむね転移する。** 実測は w=828〜1920 の写真で「幅が大きいほど AVIF 有利」。静的画像は 192〜1100 幅が中心で小さい側は不利だが、差は 1ms 級 |

**2 の後退は実在する。** それでも採るのは、比較対象が
「動く AVIF 単独」対「**128通り中81通りが 402 で壊れる**フォールバック付き」だからである。

`formats` は `next.config.ts` から**削除した**。Vercel の最適化にしか効かない設定で、
そこを通る画像がもう1枚も無い。残すと「静的画像には WebP のフォールバックがある」と
読めてしまう。

### AVIF 化してはいけない画像

| ファイル                                                 | role      | 理由                                                                                            |
| -------------------------------------------------------- | --------- | ----------------------------------------------------------------------------------------------- |
| `public/ogp.webp`                                        | `crawler` | OGP / `twitter:image`。X・Slack・LINE のクローラは AVIF を読まない                              |
| `public/images/brand/search-thumbnail-97.webp`           | `crawler` | JSON-LD の `primaryImageOfPage` と画像サイトマップ専用                                          |
| `public/images/brand/favicon.png` / `public/favicon.ico` | `crawler` | `icons.icon` / `icons.apple` と JSON-LD の `Organization.logo`。apple-touch-icon は AVIF 非対応 |
| `public/images/video-posters/access-tcu-setagaya.webp`   | `dual`    | `AppImage` と `<video poster>` の二重用途。poster の AVIF 解決は未実測で、12.9KB なので得も無い |

### 切り戻す手順

1. `AppImage` の `unoptimized={!useImgix}` を外す
2. `assets/source/` から WebP を焼き直し、`src/` のリテラルを `.webp` へ戻す
3. `next.config.ts` へ `formats` を戻す
4. この節と `image-loader.test.ts` の期待値を**同じコミットで**戻す

> [!WARNING]
> **枠が枯れている間は切り戻し先が 402 である。** 切り戻しに意味があるのは
> 枠が回復（2026-10-19〜20 ごろ）したあとだけ。

## 事前最適化の運用

```bash
pnpm images:optimize            # assets/source/** → public/** を焼き直す
pnpm images:optimize --report   # 焼かずに、いまの寸法とバイト数を表で出す
pnpm images:optimize --force    # 出力が新しくても焼き直す
pnpm check:images               # manifest の契約を検査する（CI の Static Checks と同じ）
```

- **原画像は `assets/source/` に置く。`public/` には配信するものだけを置く。**
  `public/` のバイトはそのまま「配信されるバイト」なので、予算検査が曖昧にならない。
  参照ゼロだった画像 866,691 B も `assets/source/` へ退避し、デプロイ物から 0.87 MB 減らした
- **生成物はコミットする。ビルド時に焼かない。** `public/` は Vercel のビルドキャッシュの
  対象ではないのでデプロイのたびに全再エンコードになるうえ、`sharp` のプラットフォーム別
  バイナリの取得失敗がそのまま**本番デプロイの失敗**になる。手元で焼けば
  **本番ビルドは `sharp` に一切依存しない**
- **`sharp` は新しい依存ではない。** `@img/sharp-*@0.34.5` は `next@16.1.0` の
  optionalDependency として既に `pnpm-lock.yaml` に解決済みで、`devDependencies` へ
  書いても新しい tarball も推移依存も増えない（`pnpm add -D sharp@0.34.5` の実測:
  `downloaded 0, added 0`）
- **再エンコードはビット同一にならない**（sharp / libvips のバージョン差）。だから
  CI はビット比較をせず、役割・形式・寸法・バイト予算・参照の解決だけを見る

### 目標寸法の出し方

1. 呼び出し側を**全部**拾う（`setagayafe97-image` は PageHero 9ルート＋ AboutSection ＋
   カードのフォールバック2箇所で計 13 参照ある）
2. 各呼び出しの CSS 表示ボックスを出す。固定 px はそのまま、`vw` は想定最大ビューポートで解く、
   `fill` は親の Tailwind クラス（`w-64` / `max-w-[420px]` など）から読む
3. **×2（DPR2）**
4. `object-contain` / `h-auto w-*` はボックスに収まる寸法、`object-cover` は覆う寸法
5. 全呼び出しの最大を採る
6. **原画像より大きくしない**（`withoutEnlargement: true`。imgix 側の `fit=max` と同じ理屈）

> [!NOTE]
> **`unoptimized` にした以上、レスポンシブは「ファイルの本数」と「呼び出し側の定数」へ移る。**
> 1ファイル1寸法の代償がいちばん大きいのは `setagayafe97-image`（PageHero は 70vw の
> `priority` ヒーロー、カードのフォールバックは 340px）。予算を超えたら `-card` を分けること。
