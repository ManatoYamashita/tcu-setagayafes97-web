# 画像配信の経路

画像の変換を **どこにやらせるか** を決めているドキュメント。
Lighthouse 基準値や個別の最適化手法は [`performance.md`](./performance.md) を参照。

## 結論から

**変換をやらせる先を、画像の出どころで分ける。**

| 画像の出どころ                          | 変換する場所                     | 枚数 | 変換数の上限 |
| --------------------------------------- | -------------------------------- | ---- | ------------ |
| microCMS（`images.microcms-assets.io`） | imgix（microCMS の配信）         | 93+  | 課金なし     |
| `public/` 配下の静的画像                | **Vercel の Image Optimization** | 11   | 356 / 月     |

**枠を焼いていたのは microCMS 側だけである。** 静的画像は枠 5,000 の 7% しか使わないので、
Vercel に残す。外すと LCP 要素が 4.7 倍になり、払う必要のない代償を払うことになる
（「静的画像を Vercel に残す理由」を参照）。

すべての画像は [`src/components/ui/AppImage.tsx`](../../src/components/ui/AppImage.tsx) の
`AppImage` で描く。出どころの判定は実行時に `src` を見て行うため、呼び出し側が区別する
必要は無い。

> [!IMPORTANT]
> **`next/image` を直接 import してはいけない。** `eslint.config.mjs` の
> `no-restricted-imports` が error で止める（例外は `AppImage.tsx` のみ）。

## なぜこうなったか（#237）

2026-09-19、本番の企画サムネイルが一部だけ表示されなくなった。原因は
**Vercel Free Plan の変換枠（Hobby は月5,000変換）の枯渇**である。

```
$ curl -sI 'https://setagayafes.org/_next/image?url=<microCMS画像>&w=384&q=75'
HTTP/2 402
x-vercel-error: OPTIMIZED_IMAGE_REQUEST_PAYMENT_REQUIRED
```

### 「一部だけ」になる理由を理解しておくこと

課金単位は画像1枚ではなく **変換1回**、すなわち `(元画像, 幅, 品質, フォーマット)` の
組み合わせ1つである。そして変換済みの結果は CDN に残る。したがって枯渇後はこうなる。

- 枯渇**前**に変換済み → CDN から `200` で配信され、いまも表示される
- 未変換の組み合わせ → `402` で壊れる

同一ファイルでも幅で生死が分かれる。`favicon-outline.webp` の実測。

```
200  w=320 / 384 / 420 / 512 / 640 / 750 / 1080
402  w=256 / 1200 / 1920 / 2048 / 3840
```

**画面幅と DPR で表示される画像が入れ替わるため、「ときどき一部が壊れる」という
再現しにくい形で表面化する。** 枯渇を疑う前に画像やコードを探すと何も見つからない。
**`x-vercel-error` ヘッダを最初に見ること。**

### 何が枠を食っていたか

`sizes` に固定 px を書いても、srcset には `deviceSizes` + `imageSizes` の**全候補**が並ぶ。
当時は18本あった。これに AVIF / WebP の2フォーマットが掛かる。
microCMS の企画サムネイルだけで93枚あり、News と協賛ロゴが上乗せされていた。

## imgix 側のパラメータ

`AppImage` が microCMS の画像へ付けるのは `w` / `q` / `fm=avif` / `auto=compress` /
`fit=max` の5つ。いずれも実測で決めている。

### `auto=format` は使えない

imgix の `auto=format` は Accept ヘッダを見て AVIF / WebP を出し分ける機能だが、
**microCMS の前段にある CloudFront が Accept を転送しないため機能しない。**
`Accept: image/avif,image/webp,...` を明示しても応答は `image/jpeg` のままで、
`Vary` ヘッダも返らなかった。

| 指定                         | 応答         | サイズ  |
| ---------------------------- | ------------ | ------- |
| `auto=format`（Accept 明示） | `image/jpeg` | 15,772B |
| `fm=webp&q=75`               | `image/webp` | 11,170B |
| `fm=webp&q=75&auto=compress` | `image/webp` | 8,506B  |
| `fm=avif&q=75&auto=compress` | `image/avif` | 5,651B  |

出し分けができない以上フォーマットは固定するしかない。**AVIF を選んでいる。**

### AVIF を選んだ根拠（2026-09-20 実測）

公開中の入稿画像30本（4ルート×2画面幅でブラウザが実際に取得したもの）を両形式で取り直した。

| 対象                        |        WebP |      AVIF |  削減 |
| --------------------------- | ----------: | --------: | ----: |
| 全30本                      | 1,568,048 B | 996,780 B | 36.4% |
| `/`（mobile）               |   215,776 B | 133,254 B | 38.2% |
| `/special`（mobile）        |   246,198 B | 149,855 B | 39.1% |
| `/about/sponsors`（mobile） |    70,262 B |  50,469 B | 28.2% |
| `/events`（mobile）         |   163,418 B | 121,145 B | 25.9% |

**30本すべてが `image/avif` を返した**（失敗0件）。元形式は jpg / jpeg / png / webp で、
GIF（アニメーション）は1本も無い。現在の入稿画像に透過も無い（`hasAlpha=false`）。

#### フォールバックを捨ててよい理由は4つある

1. **サポート下限がすでに AVIF を要求している。** 下限（iOS Safari 16.4 / Chrome 111 /
   Firefox 128）は TailwindCSS v4 の `@property` / `color-mix()` 由来で、AVIF の下限
   （Safari 16.0 / Chrome 85 / Firefox 93）より高い。
   **AVIF が読めない環境では、そもそも CSS が効かずレイアウトが崩れている。**
2. **本番はすでに全画像を AVIF で配っている。** `next.config.ts` の `formats` は #107 から
   AVIF 優先で、実測でも本番は `content-type: image/avif` を返す。PR #110 の
   Lighthouse 基準（Performance 98 / LCP 2.4秒）も AVIF 配信下で取った値である。
   **AVIF は新しいリスクではなく現状。**
3. **OGP は影響を受けない。** [`src/lib/metadata.ts`](../../src/lib/metadata.ts) は
   `thumbnail.url` から `w=1200&h=630&fit=fill&fill=solid&fill-color=…` を独自に組み立てており
   **`fm=` を付けない。** AVIF 非対応のクローラ（X など）には原形式（PNG / JPEG）が届く。
4. **デコードは重くならない。** 下の実測を参照。

#### デコード実測（低性能Android相当・CPU 6x）

`createImageBitmap` の所要時間のみ（7回の中央値）。

| 画像              | 幅   | WebP              | AVIF              | 差         |
| ----------------- | ---- | ----------------- | ----------------- | ---------- |
| `S__26755118.jpg` | 828  | 104,462B / 9.4ms  | 65,028B / 10.7ms  | **+1.3ms** |
| 同                | 1080 | 173,074B / 15.1ms | 104,854B / 11.3ms | −3.8ms     |
| 同                | 1920 | 249,388B / 22.7ms | 160,245B / 13.5ms | −9.2ms     |
| `UPBEAT.png`      | 828  | 11,634B / 3.2ms   | 6,808B / 4.1ms    | +0.9ms     |
| 同                | 1920 | 22,614B / 5.9ms   | 10,818B / 4.5ms   | −1.4ms     |

**悪化は最大 +1.3ms。** 幅が大きいほど AVIF のほうが速い（デコードするデータ量が少ないため）。
`/events` を Slow 4G + CPU 6x + 無限スクロール完走で通したページ計測でも、
転送 36,564B → 28,229B に対し **LCP は 1,444ms → 1,440ms で差が出なかった**（5回の中央値）。

> [!NOTE]
> 残るリスクは、企業プロキシの再エンコードのような**想定外の環境**だけである。
> 切り戻すときは [`src/lib/image-loader.ts`](../../src/lib/image-loader.ts) の `fm` と
> [`src/lib/image-loader.test.ts`](../../src/lib/image-loader.test.ts) の期待値、
> そしてこの節を同じコミットで戻すこと。

### `fit=max` は必須

imgix は既定で**拡大もする**。入稿画像の寸法は入稿者任せで、`deviceSizes` の上端（3840）に
届かないものが大半である。

| 指定                  | 実寸      | サイズ  |
| --------------------- | --------- | ------- |
| `w=1920&fm=webp&q=75` | 1920x1920 | 65,952B |
| 同上 + `fit=max`      | 1081x1081 | 35,886B |

`fit=max` が無いと、劣化した水増し画像を倍近い転送量で配ることになる。
（上表は `fm=avif` へ切り替える前の実測で、取得は `fm=webp`。倍率の話なので結論は変わらない。）

## 静的画像を Vercel に残す理由

**枠を焼いていたのは microCMS 側だけだからである。** 2026-09-20 に本番HTML（13ルート）の
srcset を全数えした結果が次である。`formats` が2つなので、変換数の上限は通り数の2倍。

| 出どころ                           | srcset の組み合わせ | ×2形式 = 上限 | 枠 5,000 に対して |
| ---------------------------------- | ------------------: | ------------: | ----------------: |
| `public/` の静的画像（11ファイル） |            178 通り |       **356** |            **7%** |
| microCMS（この13ページ分だけで）   |            386 通り |           772 |                 — |

microCMS の実際の総量はこれでは済まない。企画サムネイルだけで93枚あり、旧設定の18幅×2形式で
**約3,348変換**。News と協賛ロゴが上乗せされる（#237）。

### 「静的画像も全部 402 だった」は測り方の誤りだった

当初は静的画像も `unoptimized` にする設計だったが、その根拠にした Preview の実測は
**`curl` に `Accept` ヘッダを付けずに叩いた結果**だった。ブラウザが決して要求しない
形式変種を尋ねているので、キャッシュ済みでも 402 になる。2026-09-20 に付け直した。

| URL                        | Accept なし | Accept あり              |
| -------------------------- | ----------- | ------------------------ |
| `logo.webp` `w=640&q=60`   | 402         | **200 / 14,965B / avif** |
| `tcu-7.webp` `w=828&q=75`  | 402         | **200 / 43,181B / avif** |
| `tcu-7.webp` `w=1080&q=75` | 402         | **200 / 67,233B / avif** |

> [!IMPORTANT]
> **`/_next/image` を `curl` で検証するときは必ず `Accept` を付けること。**
> `Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8`
> 付けないと Vercel は別の形式変種を探しにいき、キャッシュ済みの画像まで 402 に見える。
> より確実なのは実ブラウザで巡回して「**実際に要求された組み合わせ**」だけを数えることである。

実ブラウザ（9ルート×2画面幅）で数えた結果、静的画像は **25通り中 23 が 200、402 は2件だけ**
（どちらもファーストビュー外の `w=750`）。一方 microCMS は 30通り中 8件が 402 だった。

### 外すと何を失うか（実測）

静的画像まで `unoptimized` にした場合のトップページ（390×844・DPR2）。

| 画像                                   | Vercel 経由 |    原寸配信 |      倍率 |
| -------------------------------------- | ----------: | ----------: | --------: |
| `tcu-7.webp`                           |      43,181 |     202,386 |     4.69× |
| `mon7a.webp`                           |      24,105 |     136,784 |     5.67× |
| **`favicon-outline.webp`（LCP 要素）** |  **16,272** |  **76,520** | **4.70×** |
| `setagayafe97-image.webp`              |      12,878 |      53,118 |     4.12× |
| `logo.webp`（ヘッダー）                |       9,021 |      51,520 |     5.71× |
| **合計（8枚）**                        | **139,856** | **653,780** | **4.67×** |

`favicon-outline.webp` は [`performance.md`](./performance.md) がトップの LCP 要素と
名指ししている画像で、`<link rel="preload" fetchPriority="high">` 付きで最優先に取りに行く。
`quality={40}` / `quality={60}` も `unoptimized` では無視される。**7% の節約のために払う額ではない。**

### 最適化キャッシュはデプロイをまたいで共有される

同じローカル画像の同じ幅を、本番と過去2つの Preview デプロイで叩くと、いずれも
`200 / 16,272B / image/avif` が返る（`age: 141119` = 39.2時間、`x-vercel-cache: HIT`）。
**デプロイのたびに変換し直す隠れコストは無い。**

### 枠の状態（2026-09-20 時点）

Vercel ダッシュボード（Hobby / All Projects / Last 30 Days）の実測。

| 指標                                     |                使用量 |
| ---------------------------------------- | --------------------: |
| **Image Optimization - Transformations** | **5.1K / 5K**（超過） |
| Image Optimization - Cache Reads         |            57K / 300K |
| Image Optimization - Cache Writes        |            29K / 100K |
| Fast Data Transfer                       |        10.7GB / 100GB |

**Hobby には請求サイクルが無く、集計は直近30日のローリング窓である**
（表示が `Aug 21, 3am - Sep 20` → 1時間後に `4am -` へ動くことで確認。支払い方法も未登録）。
つまり「◯日にリセット」という一点は存在せず、9/19〜9/20 に積んだ分が
**30日後（2026-10-19〜20 ごろ）に窓から抜ける**。それまでは未変換の組み合わせが 402 になる。
microCMS を外した後の新規消費は上限でも月356なので、窓が進めば自然に 5K を下回る。

## なぜ `AppImage` というラッパーなのか

適用方式は2つ試して、いずれも実測で否定している。

| 方式                                        | 結果                                                                                                                                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `next.config.ts` の `loaderFile` で全体適用 | **不可。** `images.loader: "custom"` は `/_next/image` を 404 にする（`dev` / `start` 双方で実測。外すと同じURLが 200）。静的画像は Vercel の最適化に残すので、この巻き添えは許容できない |
| `<Image loader={fn}>` に関数を直接渡す      | **不可。** Server Component からの受け渡しは prerender 時に `Functions cannot be passed directly to Client Components` で落ちる（`/about/sponsors` で実測）                               |

`AppImage` が `"use client"` を持つことで、呼び出し側は Server / Client を問わなくなる。
**この失敗は開発サーバーでは顕在化せず、`next build` で初めて出る。**

## 幅の候補（`deviceSizes` / `imageSizes`）

**この2つは両方の経路に効く。** `getImgProps` は `loader` の種類に関係なくここから幅を決め、
その幅をローダーへ渡すためである。つまり静的画像の Vercel 変換数と、microCMS の
imgix URL の本数を同時に決めている。**ここへ幅を1つ足すと Vercel の変換数が
「静的画像11ファイル × 2形式」ぶん増える。** 追加時は用途を PR に書くこと。

#237 で 512（`deviceSizes`）と 320（`imageSizes`）を落とした。隣接する 640 / 384 との差が
小さく、丸め先との差はそれぞれ 25% / 20% にとどまるため。2048 と 3840 は残している。
head のビルド成果物に出ている imgix URL の幅が、この16値ちょうど（512 / 320 は0本）に
なっていることで効いていることを確認できる。

## 再発防止装置は3つあり、射程が違う

| 装置                                                | 走る場所            | 守るもの                           |
| --------------------------------------------------- | ------------------- | ---------------------------------- |
| `eslint.config.mjs` の `no-restricted-imports`      | `pnpm lint`         | `next/image` の直接 import         |
| `src/lib/image-loader.test.ts`                      | `pnpm test`         | ローダー関数の**契約**             |
| `scripts/assert-remote-images-bypass-optimizer.mjs` | `pnpm build` の末尾 | ローダーが**実際に効いている**こと |

**ユニットテストだけでは足りない。** `AppImage` から `loader` / `unoptimized` の指定が
外れても、ローダー関数は無傷なのでテストは緑のまま素通りする。ビルドは通り、枠が
残っているうちは画面も正常に見える。生成物を読む以外に判定する方法が無い。

ガードは事前描画された全HTMLを走査し、**リモート画像**を `/_next/image?url=` へ渡すURLが
1本も無いことを検査する。**ローカルの静的画像は対象外**で、意図して Vercel の最適化に残している。

### 検証の記録（2026-09-19）

- 正常時: `OK`。生成物の `/_next/image` は **0件**、imgix URL は 1,514 種
- HTML へローカル画像の `/_next/image` を1本注入 → **検出して exit 1**
- `Header.tsx` で `next/image` を直接 import → **ESLint が error で停止**
- ローカル本番サーバーで主要6ページの画像を取得 → **54枚すべて 200**

### ガードが空振りする条件

microCMS の画像が1枚もHTMLに出ないと、検査対象が消える。その場合ガードは `NOTE:` を出して
成功扱いにする（入稿0件や取得失敗と区別が付かないため合否条件にしない）。

> [!IMPORTANT]
> **公開フラグが全て false でも空振りしない。** 協賛企業（`SponsorBanner` と
> `/about/sponsors`）は `NEXT_PUBLIC_*_VISIBLE` のどれにも依存せず、常に microCMS を読む。
> したがって `NOTE` が出るのは「協賛の取得が0件だった」ときであり、**それは正常ではなく
> 異常の合図である。** ログに `NOTE` が出ているときは、検査が効いていないと考えること。

## 残っている制約

- **枠は直近30日のローリング窓**なので「リセット日」は無い。9/19〜9/20 に積んだ分は
  2026-10-19〜20 ごろに窓から抜ける。それまでは未変換の組み合わせが 402 になる
  （実測では静的画像 25通り中2件だけ、どちらもファーストビュー外）
- 本対応後の Vercel 変換は静的画像だけで、上限でも月356（枠の7%）。二度と枯れない
- imgix 側には変換数の課金が無く、配信も microCMS の CDN から出る。
  つまり **Vercel の帯域（100GB/月）も消費しない**
- 静的画像の事前縮小は未了（`tcu-7.webp` 202KB / `mon7a.webp` 137KB）。
  Vercel が縮めているので急ぎではないが、原寸が大きいと変換元の読み込みが重い
