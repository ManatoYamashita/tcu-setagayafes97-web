## 「実配信HEX」は2つある。配信CSSを grep して取れるほうは誰も見ていない

Lightning CSS は色ごとに **`#hex` と `lab()` の2本**を出力する。前者は
**`lab()` 非対応ブラウザ向けのフォールバック**であり、後者が実際に描画される値である。

> [!IMPORTANT]
> **一次定義は `oklch()` だが、出力CSSに `oklch()` は1つも残らない。**
> 実測（2026-09-19 / 本番）で `oklch` は **0 件**、`lab(` は 72 件、分岐は
> `@supports (color:lab(0% 0 0))` だった。**どちらが描画されるかを決めているのは
> `lab()` への対応であって、`oklch()` への対応ではない。**
> 確かめ直すときに見る対応表を間違えないこと。

**本プロジェクトの動作下限（Safari 16.4 / Chrome 111 / Firefox 128）は全て `lab()` 対応**なので、
フォールバックの `#hex` は**サポート対象の来場者には一度も描画されない。**

自前トークン（`primary-*` / `gray-*` / `secondary`）は sRGB ガマット内にあるため
2本の値が一致し、この区別は表に出ない。**食い違うのは Tailwind 既定パレットの
彩度が高い段だけである。** 高彩度の oklch は sRGB の外にあり、フォールバックは
CSS Color 4 の「彩度を落とす」ガマットマッピングで、ブラウザは別の詰め方で描画する。

実測（2026-09-19 / 本番 / Chrome / canvas の実ピクセル）:

| 色                    | 配信CSSの `#hex`（未使用） | 実際に描画される色 | `#070707` との比         |
| --------------------- | -------------------------- | ------------------ | ------------------------ |
| `green-500`           | `#00c758`                  | **`#00c950`**      | **9.08**                 |
| `blue-500`            | `#3080ff`                  | **`#2b7fff`**      | **5.35**                 |
| `orange-500`          | `#fe6e00`                  | **`#ff6900`**      | **6.98**                 |
| `amber-500`           | `#f99c00`                  | **`#fe9a00`**      | **9.44**                 |
| `purple-500`          | `#ac4bff`                  | **`#ad46ff`**      | 3.78（`#f5f5f5` 上）     |
| `primary-400`（自前） | `#bf73e3`                  | `#bf73e3`          | 一致するので較正に使える |

> [!WARNING]
> **`grep -o -- '--color-X:#......'` で取った値でコントラストを計算してはいけない。**
> 自前トークンだけなら正しい答えが出るが、Tailwind 既定パレットでは**フォールバック＝
> 誰も見ていない色**の比が出る。差は 0.06〜0.15 と小さく、**一見もっともらしい表になる**のが厄介である。
> 2026-09-19 の #227 で、この2系統の数値が同一PR内に別々の表として同居した。

**How to apply:** 既定パレットの比を出すときは配信CSSを読まず、**実ブラウザで
`getComputedStyle` の値を canvas に塗り、実ピクセルを読む。** 色空間の変換も
不透明度の合成もブラウザ自身にやらせられるので、1回で正しい sRGB が出る。

```js
const cv = document.createElement("canvas");
cv.width = cv.height = 1;
const cx = cv.getContext("2d", { willReadFrequently: true });
const toHex = (cssColor) => {
  cx.fillStyle = "#000";
  cx.fillRect(0, 0, 1, 1); // 下地を固定
  cx.fillStyle = cssColor;
  cx.fillRect(0, 0, 1, 1); // lab() / oklch() をそのまま渡せる
  const d = cx.getImageData(0, 0, 1, 1).data;
  return "#" + [d[0], d[1], d[2]].map((v) => v.toString(16).padStart(2, "0")).join("");
};
toHex(getComputedStyle(el).backgroundColor); // => "#00c950"
```

どちらを見ているか分からなくなったら、`primary-400` が `#bf73e3` になることを較正点にする。

## コントラスト比（アクセシビリティ）

WCAG 2.1 に準拠した最低基準。

**すべて実配信値で算出している**（仕様 HEX ではない）。

| 組み合わせ                                           | コントラスト比 | 適用基準                         |
| ---------------------------------------------------- | -------------- | -------------------------------- |
| **gray-900 `#070707` on Secondary `#d5a7ed`**        | **10.2:1**     | **✅ WCAG AAA 適合（推奨）**     |
| gray-900 `#070707` on `#FFFFFF`（白背景）            | 20.1:1         | ✅ WCAG AAA 適合                 |
| gray-700 `#3a3a3a` on `#FFFFFF`                      | 11.4:1         | ✅ WCAG AAA 適合                 |
| gray-600 `#555555` on `#FFFFFF`                      | 7.5:1          | ✅ WCAG AA 適合                  |
| primary-400 `#bf73e3` on `#FFFFFF`（白背景）         | 3.1:1          | ⚠️ WCAG AA（大テキスト・UI）のみ |
| **primary-700 `#592072` on Secondary（淡紫背景）**   | **5.6:1**      | **✅ WCAG AA 適合（推奨）**      |
| primary-600 `#7b359a` on Secondary（淡紫背景）       | 3.8:1          | ⚠️ 大テキスト・UI のみ           |
| primary-300 `#cb8fe8` on Secondary（淡紫背景）       | 1.2:1          | ❌ 前景色として使用禁止          |
| `#FFFFFF` on primary-400 `#bf73e3`（Primary 紫背景） | 3.1:1          | ⚠️ 大テキストのみ使用可          |
| `#FFFFFF` on Secondary `#d5a7ed`（淡紫背景）         | **2.0:1**      | ❌ **前景色として使用禁止**      |

> **重要**:
>
> - **推奨組み合わせ**: gray-900（黒テキスト）on Secondary（淡い紫背景）— コントラスト比 10.2:1 で WCAG AAA 適合
> - Primary 紫（primary-400 / 実配信 `#bf73e3`）は**白背景での通常テキストに使用禁止**（3.1:1）。CTA リンク・装飾的な見出し・アクセントカラーとしての利用に限定すること。
> - **Secondary 紫（実配信 `#d5a7ed`）の上に白テキストを置いてはいけない。** 実配信値でのコントラストは **2.0:1** しかなく、大テキストの 3:1 にも届かない。仕様 HEX `#E1C0EE` で計算しても 1.6:1 で、旧記載の「約 5.2:1・大テキストなら可」は誤りだった（2026-08-30 訂正）。
> - **`--color-primary-light`（primary-300）を前景テキスト・アイコンに使ってはいけない。** 淡紫背景で 1.2:1、白10%を重ねたカードでも 1.3:1 しかなく、背景とほぼ同色になる。暗色背景時代の名残であり、装飾用途に限ること。
> - **リンク色は背景で使い分ける。** 白背景は `--color-primary-dark`（primary-600 / 7.5:1）、淡紫背景（`bg-secondary` や `bg-white/10` のカード）は `primary-700`（5.6:1）。`primary-dark` は淡紫背景では 3.8:1 で AA に届かない。
> - **`bg-white/10` の見え方は下地で決まる。** 淡紫のページ背景の上では白を 10% 重ねただけで背景とほぼ同じ明度になり、`PageSheetLayout` の白いシート（`bg-white`）の上では**純白**になる。同じ理屈で `border-gray-200/20` は白いシート上で 1.08:1 となり消える。カード内の色は「どのシートの上にあるか」を見てから選ぶこと。

### 白文字 on ブランドカラーは ESLint が落とす（#95）

この規則は 2026-08-24 に #95 で起票され、`globals.css` にも当時の design.md にも書かれていたが、
**2026-09-22 の監査時点で8箇所に残っていた**（うち7箇所が文字で不適合、1箇所はアイコンのみ）。 文書は人間が読まなければ効かないため、
`eslint.config.mjs` の `WHITE_ON_BRAND_PATTERN` が装置として落とす。

同じ className 文字列に `bg-primary` / `bg-accent` / `bg-primary-400` 以下の段と
`text-white` が同居したら `pnpm lint` が exit 1 になる。

| 背景          | 白文字との比 | 判定    |
| ------------- | ------------ | ------- |
| `primary-400` | 3.10:1       | ❌      |
| `primary-500` | 4.88:1       | ⚠️ 可   |
| `primary-600` | 7.45:1       | ✅ 推奨 |
| `primary-700` | 11.2:1       | ✅ 推奨 |

> [!NOTE]
> **規則は className の文字列しか見えないため、2種類の正当な用法まで落とす。**
>
> | 落ちるが正しい場合 | 根拠                                         |
> | ------------------ | -------------------------------------------- |
> | 中身がアイコンだけ | 非テキストコントラスト（1.4.11）の要求は 3:1 |
> | 大テキスト         | 18.66px 太字 / 24px 以上の要求は 3:1         |
>
> どちらも 3.10:1 で**基準を満たす**。該当したら
> `// eslint-disable-next-line no-restricted-syntax -- 理由` で外し、**理由を必ず書く**
> （実例は `src/components/ui/PageHero.tsx` の CTA の円）。
> **余裕は 0.10 しかないので、外したうえでさらに色を薄くしてはいけない。**
>
> 射程外（落とせない形）は `eslint.config.mjs` の `WHITE_ON_BRAND_PATTERN` のコメントを参照。

### 淡紫グラデーションの上では、白地の値では足りない（#270）

**Hero とトップの前半は白ではない。** `.hero-about-bg` が
`#ffffff` → `primary-50` → `primary-100` → `secondary` の縦グラデーションで塗っており、
日付ブロックの位置では `rgb(240,217,251)` 前後になる。

| 前景          | Hero 日付位置 | 白地    |
| ------------- | ------------- | ------- |
| `primary-400` | **2.36:1**    | 3.10:1  |
| `primary-500` | **3.72:1**    | 4.88:1  |
| `primary-600` | **5.69:1**    | 7.45:1  |
| `primary-700` | **8.55:1**    | 11.20:1 |

**`primary-500` は白地なら通常テキストで通るが、ここでは通らない。**
淡紫の上の通常テキストは `primary-600` 以上が要る。

2026-09-23 の測定（本番 / 1440×900）では、変更前の Hero が次の状態だった。

| 要素            | サイズ       | 変更前     | 要求  | 変更後     |
| --------------- | ------------ | ---------- | ----- | ---------- |
| `2026`          | 16px         | 2.44:1     | 4.5:1 | **8.79:1** |
| 日付の数字      | 72px         | 2.37:1     | 3:1   | **8.59:1** |
| `Sat` / `Sun`   | 14px         | 2.33:1     | 4.5:1 | **8.42:1** |
| `10:00 - 19:30` | 14px（α0.7） | **1.78:1** | 4.5:1 | **5.55:1** |

> [!IMPORTANT]
> **72px の数字が 2.37:1 で、大テキストの 3:1 すら満たしていなかった。**
> 「大きい文字だから 3:1 で足りる」は、地が白のときの話である。
>
> **不透明度で階層を作らないこと。** 時刻行は `text-primary-400/70` だったため
> 1.78:1 まで落ちていた。`primary-700/70` にしても 4.09:1 で届かない。
> 階層は**段で作る**（日付は `primary-700`、時刻は `primary-600`）。

**この背景は静的解析で見えない。** グラデーションは祖先要素にあり、
テキストの className には現れない。実画面で canvas へ 1px 描いて測ること
（`getComputedStyle` は `lab()` を返すので、その文字列をパースしてはいけない）。

### 前景色に別名 `text-primary` / `text-accent` を書かない（#270）

`--color-primary` も `--color-accent` も `primary-400`（実配信 `#bf73e3`）の別名で、
**白地の通常テキストでは 3.10:1** しかない。`eslint.config.mjs` の
`BRAND_TEXT_ALIAS_PATTERN` が落とす。

| 前景          | 白地       | `bg-primary/10` の上 |
| ------------- | ---------- | -------------------- |
| `primary-400` | 3.10:1     | 2.81:1               |
| `primary-500` | 4.88:1     | 4.42:1               |
| `primary-600` | **7.45:1** | 6.75:1               |
| `primary-700` | **11.2:1** | 10.15:1              |

- 通常テキスト → `text-primary-600`
- アイコン・大テキスト（要求 3:1）で意図して使う → **`text-primary-400` と明示的に書く**

> [!IMPORTANT]
> **これはコントラストの保証ではない。** `text-primary-400` と書けば規則は通る。
> 保証しているのは「どの段を選んだかがコードに書いてある」ことだけで、
> **以降の監査が数値トークンの正確な grep で済む**ようになる。
>
> **本来守りたい「ブランド紫を通常テキストに使わない」は装置にできない。**
> 可否が下地で決まり、**下地は同じ className に書かれていない**（親要素・シート・
> グラデーション・写真のいずれか）。2026-09-22 に「アイコンと大テキストを
> 除外する」近似規則を実装して実測したところ、**20件中5件が正しいコードを
> 落とす偽陽性**だった（暗色パネル上の `primary-200`、`primary-700` 上の
> `primary-50`、5% の装飾SVG、子要素が大テキストの親、高さクラスの無い装飾SVG）。
> **初回から5件の disable を要求する装置は、disable を習慣にするだけで機能しない。**
> 反証の詳細は `eslint.config.mjs` の `BRAND_TEXT_ALIAS_PATTERN` のコメント、
> 残件は #270 を参照。

> [!WARNING]
> **[design.md](./design.md) のカラースケール表と本ファイルのコントラスト表は、実際に配信される色（実配信値）で書いてある。** カラースケールは `@theme` で oklch 指定しており、Lightning CSS がビルド時に変換するため、デザイン仕様の HEX とは別の値が配信される。例: Secondary は仕様 `#E1C0EE` に対して実配信 `#d5a7ed`、ブランドカラーは仕様 `#CD79EE` に対して実配信 `#bf73e3`。**仕様 HEX が載っているのは design.md のブランドカラーの属性表だけで、そこには実配信 HEX を併記してある。**
>
> 上の表は**すべて自前トークンどうしの組み合わせ**で、いずれも sRGB ガマット内にあるため、次の grep で取れる値と実際の描画色が一致する。
>
> ```bash
> grep -o -- '--color-secondary:[^;]*' $(find .next -name '*.css' -path '*static*' | head -1)
> ```
>
> **ただし Tailwind 既定パレットには使えない。** 出力CSSには `#hex` と `lab()` の**2本**が出ており、この grep が拾うのは `oklch()` 非対応ブラウザ向けのフォールバックである。ガマット外の既定パレットでは両者が食い違う。詳細と実測は本ファイルの「『実配信HEX』は2つある」節を参照。
