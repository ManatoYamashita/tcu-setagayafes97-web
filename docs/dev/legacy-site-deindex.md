# 過去回サイト群の検索除外（noindex 運用）

## 決定

**検索結果に出るのは第97回サイト（`setagayafes.org`）だけにする。** 過去回サイトと
補助サイトは、URLを知っていれば閲覧できるまま残し、検索結果からだけ外す。

削除も 301 統合もしない。閲覧を残す方針に反するためである。

> [!WARNING]
> **`todorokifes.setagayafes.org` は対象外。** これは第13回東京都市大学**等々力祭**の
> 公式サイトであり、世田谷祭の過去回ではない。「`setagayafes.org` のサブドメインを
> 一括で noindex」という操作をすると巻き添えで消える。**ホストごとに個別に設定すること。**

## なぜこの構成になっているか

Google に残っていた「第96回」の検索結果（2026-09-03 実測）は、実体が
`setagayafes.org/96th/about/` と `setagayafes.org/sfa/` である。**どちらも既に 301 を
返しており、コード側に欠陥は無い。** Google が 301 を再処理していないだけの残像である。

一方 `about.` と `archive.` は**今も index 可能**で、こちらは残像ではない。第96回が
消えても第95回以前が代わりに出続ける。恒久解はこの2ホスト（と `blog.` `form.` `link.`）
への `X-Robots-Tag` 付与だけである。

## さくら側の手順

### 0. 公開フォルダを特定する（必須）

`.htaccess` は「そのホストのドキュメントルート」に置かないと効かない。既知なのは
96th の `~/www/top/96th` だけ（`domain-migration.md`）。残りはコントロールパネルで確認する。

1. さくらのコントロールパネル → **ドメイン／SSL** → 各ドメインの「設定」
2. **公開フォルダ**の値を控える

SSH が使えるなら `ls -la ~/www/top/` で一覧できる。

> [!IMPORTANT]
> **`~/www/top` そのものに置かないこと。** そこへ公開フォルダを持つ他ホストへ波及する。
> 必ず「そのホストの公開フォルダ」に置く。

### 1. 96th の既存 `.htaccess` を写経元にする

新しく書き起こすより、このサーバで実際に動いている記述をコピーするほうが確実である。

```bash
cat ~/www/top/96th/.htaccess
```

ファイルマネージャーの場合は「表示 → 隠しファイルを表示する」を有効にしないと
`.htaccess` が一覧に出ない。

### 2. 5ホストへ追記する

`about` / `archive` / `blog` / `form` / `link` の各公開フォルダ直下の `.htaccess` へ。

```apache
# BEGIN setagayafes-noindex
# 第97回サイト(https://setagayafes.org)だけを検索結果に出すための指定。
# 閲覧はこれまでどおり可能。URLを知っていれば普通に見られる。
# robots.txt でのクロール禁止は絶対にしない（Googlebot がこの行を読めなくなるため）。
# 追加日: YYYY-MM-DD  担当: XXX  関連: docs/dev/legacy-site-deindex.md
Header always set X-Robots-Tag "noindex, noimageindex"
# END setagayafes-noindex
```

- `Header always set` にする。`set` だけだと 404 や 301 のレスポンスに付かない
- **`<FilesMatch>` で絞らない。** 画像・PDF にも効かせる必要がある。HTML だけに絞ると
  パンフレットPDFや配置図画像が検索結果に残り続ける
- **`nofollow` は足さない。** リンクを辿らなくなると、深い階層
  （`/88th/visitors/index.htm` など）の noindex 発見が遅れる。今回の目的は
  「全ページを速やかに再クロールさせて noindex を見せる」ことである

> [!WARNING]
> **WordPress（`about` / `blog`）は `# BEGIN WordPress` より前に書くこと。**
> WordPress は「設定 → パーマリンク → 保存」を押しただけでこのブロックをまるごと
> 書き直す。中に書いた行は予告なく消え、しかも消えたことに誰も気づかない。

### この方法が動く根拠（実測）

`96th.setagayafes.org` では、静的な `.webp` 画像・`.css`・`.xml`（いずれも 200）と、
存在しないURLの 404 応答のすべてに `x-robots-tag: noindex, noimageindex` が付いている。
**WordPress や AIOSEO では静的ファイルと 404 にヘッダを付けられない。** つまり既に
`.htaccess` の `Header` が効いており、同じ記述が残り5ホストでも動く。

### 3. `robots.txt` には触らない

> [!WARNING]
> **`robots.txt` で `Disallow: /` を書いてはいけない。** クロールを止めると Googlebot が
> `X-Robots-Tag: noindex` を**永久に読めなくなり**、URLは「タイトルもスニペットも無い、
> URLだけの検索結果」として居座り続ける。noindex を後から入れても読まれないので、
> 打つ手が無くなる。**この計画で唯一、後から取り返せない失敗である。**

| ホスト             | 現在の robots.txt                                                      | 対応                                 |
| ------------------ | ---------------------------------------------------------------------- | ------------------------------------ |
| `archive` / `blog` | 物理ファイル。`Disallow: /errorpage/` のみ                             | 触らない                             |
| `about`            | **WordPress の仮想ファイル**。`Disallow: /wp-admin/` + `Sitemap:` 宣言 | 触らない                             |
| `96th`             | 404（物理ファイルなし）                                                | 触らない。「無いのを直そう」としない |

> [!WARNING]
> **WordPress の「設定 → 表示設定 → 検索エンジンでの表示」にチェックを入れないこと。**
> このチェックは仮想 robots.txt を `Disallow: /` に書き換える。`about` は robots.txt が
> 仮想なので、まさにこの罠に直撃する。
> **Basic認証・IP制限・さくらの「サイト非公開」も同じ理由でNG。** 401/403 は noindex を読ませない。

### 4. サイトマップの扱い

**ファイルは残し、Search Console の送信一覧からだけ消す。** サイトマップは Googlebot に
「このURL群を再クロールしろ」と教える一括導線であり、noindex を早く見せたい今は
あったほうが有利である。`.htaccess` の Header によりサイトマップ自身にも noindex が付く。

`about.setagayafes.org/robots.txt` の `Sitemap:` 宣言も残す（仮想ファイルなので消すには
プラグインかフィルタが要り、変更点が増えるだけで得が無い）。

### 5. 適用直後の検証（コピペ実行可）

```bash
# noindex が付くべき6ホスト
for h in 96th about archive blog form link; do
  printf '%-14s ' "$h"
  curl -sSI -m 15 "https://$h.setagayafes.org/" | tr -d '\r' \
    | awk -F': ' 'tolower($1)=="x-robots-tag"{print $2}' | grep . || echo '!! noindex が付いていない'
done

# 付いてはいけないホスト
printf '%-14s ' todorokifes
curl -sSI -m 15 https://todorokifes.setagayafes.org/ | tr -d '\r' \
  | awk -F': ' 'tolower($1)=="x-robots-tag"{print $2}' | grep . \
  && echo '!! 巻き添え。ただちに外す' || echo 'OK（なし）'

# 第97回に付いていないこと（最重要の安全弁）
printf '%-14s ' apex
curl -sSI -m 15 https://setagayafes.org/ | tr -d '\r' \
  | awk -F': ' 'tolower($1)=="x-robots-tag"{print $2}' | grep . \
  && echo '!! 事故。全作業を中止して原因を追う' || echo 'OK（なし）'

# 静的ファイルにも効いているか
curl -sSI -m 15 https://archive.setagayafes.org/94th/hello/index.htm | grep -i x-robots-tag

# クロールを止めていないこと
curl -sS https://archive.setagayafes.org/robots.txt
curl -sS https://about.setagayafes.org/robots.txt
```

### 6. ロールバック

**この作業に「元に戻せない操作」は一つも無い。** ファイル削除もDB変更もしていない。

| 症状                           | 原因                               | 復旧                                                                                                                                |
| ------------------------------ | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 500 Internal Server Error      | `Header` が解釈されなかった        | 追記したブロックを削除して保存。数秒で復旧。96th の `.htaccess` の書き方（`<IfModule mod_headers.c>` で包んでいるか等）に合わせ直す |
| ヘッダーが出ない（200 だが空） | 公開フォルダを間違えた             | 手順0へ戻る                                                                                                                         |
| about / blog で追記が消えた    | `# BEGIN WordPress` の内側に書いた | マーカーの外側へ移す                                                                                                                |

## Search Console の手順

**さくら側の noindex が全ホストで確認できてから着手する。** 順序を誤ると、削除申請が
約6ヶ月で失効したときに noindex が無く、古いページが復活する。

### 1. プロパティを整える

| 種別               | 登録するもの                                | 役割                                                                                                                                                                                 |
| ------------------ | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ドメインプロパティ | `setagayafes.org`                           | 1回の DNS 確認で apex + www + 全サブドメインをカバー。削除ツールをサブドメインへ使う最短経路                                                                                         |
| URLプレフィックス  | apex と `96th.` `about.` `archive.` `blog.` | **進捗を読むために必須。** 「ページのインデックス作成」レポートはプロパティ単位でしか集計されず、ドメインプロパティだけだと「archive の何件が noindex で落ちたか」が原理的に読めない |

DNS はさくらが権威（`ns1.dns.ne.jp` / `ns2.dns.ne.jp`）なので、確認用 TXT はさくらの
ゾーン編集へ入れる。**さくらのゾーン編集は2段階で、「変更」の後に「送信する」まで
押さないと反映されない。**

```bash
dig +short TXT setagayafes.org | grep google-site-verification
```

### 2. 削除ツール（一時的な削除）

**これは約6ヶ月の目隠しであって削除ではない。** 単独では意味がなく、6ヶ月後に
そのまま元に戻る。サーバー側 noindex が効くまでの数週間を埋めるためだけに使う。

「URL を一時的に削除する」→「このプレフィックスを含む URL をすべて削除」で以下を登録。

```
https://archive.setagayafes.org/
https://about.setagayafes.org/
https://blog.setagayafes.org/
https://form.setagayafes.org/
https://link.setagayafes.org/
https://96th.setagayafes.org/
https://setagayafes.org/96th/
https://setagayafes.org/95th/
https://setagayafes.org/sfa/
```

> [!CAUTION]
> **`https://setagayafes.org/` をプレフィックス指定してはいけない。** 第97回サイト全体が
> 約6ヶ月間 検索結果から消える。会期直前にやると回復不能な機会損失になる。
> プレフィックスは末尾の `96th/` `95th/` `sfa/` まで含めて入力し、送信前に確認画面のURLを
> 声に出して読むこと。**`todorokifes.` も申請しない。**

### 3. サイトマップ

- `96th.` と `about.` のサイトマップは Search Console の**送信一覧から削除**する
  （サーバー上のファイルは残す。上記「4. サイトマップの扱い」を参照）
- `https://setagayafes.org/sitemap.xml` を再送信する

### 4. URL検査でインデックス登録をリクエスト

1日十数件のクォータがある。上から順に。

**Day 1** — `/`、**`/about`**、`/events`、`/timetable`、`/access`

`/about` は `about.setagayafes.org/` と `setagayafes.org/sfa/` の置き換え先である。
消す側と同時に強化しないと「世田谷祭とは」「世田谷祭実行委員会」の検索結果が一時的に
空白になる。**「世田谷祭とは」セクションが本番へ出てから**リクエストすること。

**Day 2** — `/info`、`/info/guide`、`/info/faq`、`/info/pamphlet`、`/special/special-event-mon7a`

**Day 3 以降（任意）** — 消したい側のURLにもリクエストを打てる。矛盾しているようだが、
これは「Googlebot に取りに来させる」操作であり、取りに来た結果 noindex を見て落とす。

### 5. やってはいけないこと

| #   | 操作                                           | 何が起きるか                                                                                         |
| --- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | robots.txt で `Disallow: /` してから削除申請   | 最悪。noindex を永久に読めず、6ヶ月後に「URLだけの検索結果」として復活し、以後どう対処しても消えない |
| 2   | WordPress の「検索エンジンでの表示」にチェック | #1 と同じ。`about` は仮想 robots.txt なので直撃する                                                  |
| 3   | Basic認証 / IP制限 / サイト非公開              | 401/403 で noindex が読めない。#1 と同じ結末                                                         |
| 4   | `https://setagayafes.org/` を削除申請          | 第97回サイト全体が約6ヶ月非表示                                                                      |
| 5   | 削除申請だけで終わりにする                     | 6ヶ月後に全部戻る。しかもその間は消えているので気づけない                                            |
| 6   | サーバーからファイルを削除 / サイトを閉じる    | 「閲覧は残す」方針に反する。404 は noindex より除外が遅いことがある                                  |
| 7   | `/95th/*` などから archive へ 301 を張る       | 消したいURLへ新しい発見経路を作る。逆効果                                                            |
| 8   | サイトマップ**ファイル**を削除 / 生成を OFF    | 再クロール導線が減り、noindex の反映が遅くなる                                                       |
| 9   | `site:` 検索の結果だけで完了判定               | 概算でありブレが大きい。判定は Search Console の「ページ」レポートで行う                             |

再生成、さくらのサーバー移設・プラン変更、そして**別の作業者が「なぜか noindex に
なっている」と考えて善意で削除する**ことである。最後が最も多い。だから `.htaccess` に
理由と本ファイルへの参照をコメントで書く。

## 採用しなかった選択肢

| 案                                        | 却下理由                                                                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `about.` → `setagayafes.org/about` へ 301 | インデックス除外は最速で評価も統合できるが、「URLを知っていれば閲覧できるまま残す」方針に反する。将来「閲覧不要」と決まったら、noindex より 301 のほうが優れている |
| 全ホストを `410 Gone` にする              | 同上。閲覧不可になる                                                                                                                                               |
| Vercel 側で `/95th/*` → archive へ 301    | 消したいURLへ発見経路を作る逆効果（やってはいけないこと #7）                                                                                                       |
| WordPress の SEO プラグインで全体 noindex | WP が描画するページにしか効かず、`wp-content/uploads/` の画像・PDF に効かない                                                                                      |
