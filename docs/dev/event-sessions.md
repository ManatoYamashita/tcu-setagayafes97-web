# 企画の開催枠（sessions）

2部制のように、1つの企画が時間を空けて複数回開催される場合の扱い（#281）。

## 背景

Events API の時刻は、もともと `startTime` / `endTime` の1組しかなかった。
カレッジフェスタコレクション（10:40〜11:25 / 14:30〜15:30 の2部制）は 10:40〜15:45 の1枠で入稿するしかなく、
**空き時間の 11:25〜14:30 も開催中として**、次の3箇所に出ていた（終了の 15:45 も誤り。下の注記）。

| 箇所               | 誤っていた出力                                             |
| ------------------ | ---------------------------------------------------------- |
| 詳細ページの時刻   | `10:40 〜 15:45`                                           |
| JSON-LD            | `startDate …T10:40` 〜 `endDate …T15:45`                   |
| タイムテーブル盤面 | 5時間の帯が1本（同じ列の空き時間の企画とレーンを取り合う） |

> [!NOTE]
> **委員会から最初に届いた時刻（第2部 14:45〜15:45）は誤りだった。** 正しくは 14:30〜15:30 で、
> 入稿済みの本文の出演順（`14:30-14:45 idoress` 〜 `15:15-15:30 NEW FRONTIER`）のほうが合っていた。
> 本文と要望の食い違いには #281 の調査の時点で気づいていたが、要望のほうを採って入稿した。
> 2026-09-28 に委員会へ確認し直して訂正した。**要望の時刻が入稿済みのデータと食い違ったら、
> 入稿や実装の前に、どちらが正しいかを委員会に確かめること。**

企画を2件に分ける案は採らなかった。本文・画像・特典会の情報が二重になり、一覧にも2枚並ぶ。
`startTime2` / `endTime2` を固定で足す案も採らなかった。3部制が来たら同じ改修をやり直すことになる。

## スキーマ

| フィールドID | 表示名 | 型       | 必須     | 参照先    |
| ------------ | ------ | -------- | -------- | --------- |
| `sessions`   | 開催枠 | repeater | **任意** | `session` |

カスタムフィールド `session` は `date`（日程。`select`）/ `startTime`（開始時刻）/ `endTime`（終了時刻）の3つで、すべて任意項目。
`date` は #305 で追加した（下の「日程を持つ開催枠」）。
スキーマ写しは [`microcms/events.json`](../../microcms/events.json)。

> [!IMPORTANT]
> **`sessions` を必須にしてはいけない。** 必須にすると、`sessions` の無い既存の企画を次に編集したとき、
> 入力を求められて保存できなくなる。

## 正規化の契約

規則は `normalizeEventSessions()`（[`src/lib/event-sessions.ts`](../../src/lib/event-sessions.ts)）の1箇所にある。
`normalizeEvent()` がこれを呼んで `Event.sessions` を作る。

| 入稿の状態                                  | `Event.sessions`                             |
| ------------------------------------------- | -------------------------------------------- |
| `sessions` に値の入った行がある             | その行（**`startTime` / `endTime` は無視**） |
| `sessions` が無い／`[]`／値の無い行しか無い | `startTime` / `endTime` から1枠              |
| どちらも空                                  | `[]`（時間未定）                             |

- 値は trim する。**HH:mm として読めるかは検査しない**（詳細ページは入稿どおりに出す）
- **日程（1日目 → 2日目。日程の無い枠は1日目の側）→ 開始時刻**の順に並べる。同じ日の中で読めない枠は末尾に置き、それらどうしは入稿順を保つ
- 枠の日程は `day1` / `day2` だけを読む。`both` / `other` / 未入力は「日程の指定なし」とし、**`date` キーを持たせない**
- 値の無い行を落とすのは、管理画面で行を足しただけの状態で、従来の欄まで黙って無視されないようにするため

> [!IMPORTANT]
> **正規化後の `Event` には `startTime` / `endTime` が無い**（型にも実行時の値にも）。
> 先頭の枠だけを読むコードを書くと型エラーになるので、第2部以降を落とす実装はコンパイルの時点で止まる。
> `normalizeEvent()` で `...rawEvent` の前に分割代入して外しているのはそのため。
> 型から消しても実行時に値が残っていれば、`as` などで型検査を迂回したコードが動いてしまう。

## 表示

| 場所                   | 出し方                                                                                                                                            | 実装                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 詳細ページ「開催時間」 | 枠ごとに1行。2枠以上なら `第1部 10:40 〜 11:25` の形                                                                                              | `formatSessions()`                                             |
| 企画カード             | `10:40 - 11:25 / 14:30 - 15:30`。「第n部」は付けない。1枠の企画は終了が無ければ出さない（従来どおり）。2枠以上なら終了の無い枠も `14:30〜` で出す | `formatSessions(…, { requireEnd: 枠が1つ, withLabel: false })` |
| 著名人企画LP「開演」   | 詳細ページと同じ                                                                                                                                  | `formatSessions()`                                             |
| JSON-LD                | 親は最初の開始〜最後に終わる枠の終了。2枠以上なら枠ごとの `subEvent`。時刻は分から組み立て直して2桁に揃える                                       | `buildEventScheduleJsonLd()`                                   |
| タイムテーブル         | 枠ごとに別ブロック                                                                                                                                | [timetable-gantt.md](../frontend/timetable-gantt.md)           |

「第n部」は、**同じ日に表示する枠**が2つ以上あるときだけ付ける（`labelSessions()`）。1枠の企画に付けると、続きがあるように読めてしまう。
日程を持つ枠の扱いは次節。

- 開始時刻の無い枠はどこにも表示しないので、数える前に落とす。落とす前の数で数えると、1枠しか見えないのに「第1部」と付く
- 開始時刻が入っていれば、HH:mm として読めなくても数に入れる（詳細ページは入稿どおりに出す）。タイムテーブルはその枠を描けないが、呼び名は詳細ページと揃える

## 日程を持つ開催枠（#305）

両日開催（`date: both`）で、日によって時刻が違う企画のための仕組み。実データの Jazz Festival
（1日目 11:00–16:00 / 2日目 11:00–15:00）は、終了時刻の欄に `1日目16:00　　2日目15:00` と書くしかなく、
タイムテーブルと JSON-LD から消えていた。

**枠に `date`（`day1` / `day2`）があれば、その枠はその日だけに開催される。** 無い枠は従来どおり企画の `date` に従う。

| 場所                 | 出し方                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------ |
| 詳細ページ・著名人LP | `1日目 11:00 〜 16:00` / `2日目 11:00 〜 15:00`                                            |
| 企画カード           | `1日目 11:00 - 16:00 / 2日目 11:00 - 15:00`。**「第n部」を付けないカードでも日程は付ける** |
| タイムテーブル       | 枠の日程の日だけにブロックを出す（`TimetableEntry.date` = 枠の日程 ?? 企画の日程）         |
| JSON-LD              | 枠の日程の日付で組み立てる。親の範囲は日付込みで比べる                                     |

- 「第n部」は**同じ日の枠の中で**数える。各日1枠の企画に「第1部 / 第2部」を付けると、2部制に読める
- 「1日目」などは、**表示する枠の日程が2種類以上あるときだけ**付ける。1日だけの企画に付けても情報が増えない
- 盤面のブロックには「1日目」を付けない（日ごとの盤面なので自明。`sessionLabel` には「第n部」だけが入る）
- **日程の無い `both` 企画の JSON-LD は、この変更の後も1日分しか出ない**（#289）。詳細ページは 11月1日、著名人LP は 10月31日に寄せており、ページ間でも食い違っている

企画を日ごとの2件に分ける案は採らなかった（上の #281 と同じ理由）。終了を片方の日に揃える案も、もう一方の日に誤った時刻を出すので採らなかった。

## 時刻欄に入れてよいのは `HH:mm` だけ（#305）

**`startTime` / `endTime` と、`session` の `startTime` / `endTime` には `HH:mm` だけを入れる。**
開場時刻や日ごとの差を書き添えると、タイムテーブル・JSON-LD・並び替えのすべてで時刻として読めず、
**エラーも出さずに企画がタイムテーブルから消える**（本番の警告は出さない。開発時の `console.warn` だけ）。
2026-09-30 に実データ99件中3件がこれに当たっていた。

| 書きたいこと     | 置き場                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 開場時刻         | 専用欄 `special.openTime` に入れる。**企画の種別を問わず**、値があればタイムテーブルのカードに「開場 HH:mm」で出る（著名人企画は LP の「開場」にも出る）。専用欄を使わない場合は説明文（`description`）へ。説明文の時刻はタイムテーブルに出ない |
| 日ごとに違う時刻 | 開催枠の `date`（上の節）                                                                                                                         |
| 雨天時の代替など | 本文（`content`）                                                                                                                                 |

**コード側で自由記述を読み解くことはしない。** 詳細ページは入稿値をそのまま出す契約なので、
タイムテーブルだけで先頭の時刻を拾うと、画面ごとに表示が食い違う。書き方の種類が増えるたびに規則も増える。

再発は microCMS の入力制限（テキストフィールドの「特定のパターンのみ入力を許可する」）で止める。
4欄とも `^(([01]?[0-9]|2[0-3]):[0-5][0-9])?$` を設定する。空欄（時間未定）は正規表現そのもので許しており、
入力制限の仕様（空欄をどう扱うか）には頼らない。

**2026-09-30 に4欄とも設定済み**（`microcms/events.json` の `patternMatchValidation` がエクスポートの実値）。
新規追加画面で開始時刻にだけ `17:00(開場16:30)` を入れて「下書きを保存」を押すと、
「指定された形式にマッチしていません」で保存が止まることを確かめた。確かめるときは既存の企画で試さないこと
（制限が効いていなければ、そのまま保存・公開されてしまう）。

## JSON-LD の日時

JSON-LD の日時は次の規則で組み立てる（レビューで3件の塵が出た箇所。#284）。

- **入稿値の文字列を埋め込まない。** `parseTimeToMinutes()` は `9:30` のような1桁の時も受け付けるので、そのままだと `T9:30:00` という不正な日時になる。分から組み立て直して2桁にする
- 親の終了は**組み立て直した日時で比べる**。入稿値の文字列で比べると `9:50` が `11:00` より後になる。時刻だけで比べると、日程を持つ枠で1日目の 16:00 が2日目の 15:00 より後になる（#305）
- 最後の枠に終了が無いときは、親の `endDate` を出さない。出すと `subEvent` が親の期間からはみ出す
- 両日開催（`both`）の企画は 11月1日の企画として出る。既存の問題で、#289 で扱う

## 入稿の手順

1. microCMS の Events API に、カスタムフィールド `session` → 繰り返しフィールド `sessions` の順で追加する（**任意**にする。作成順序は [microcms.md](./microcms.md) の「作成順序は子から親へ」）
2. 2部制の企画だけ、`sessions` に枠を1行ずつ入れる。**本文に出演順などの時刻があれば、枠と食い違っていないか確かめる**（背景の注記）
3. 日によって時刻が違う両日開催の企画は、枠ごとに「日程」を選ぶ（#305）
4. 他の企画は触らなくてよい

手順1は 2026-09-28 に実施済み（`session` / `sessions` とも任意）。

**このコードが本番に出る前に `sessions` だけを入れても、画面には反映されない**（古いコードは `startTime` / `endTime` しか読まない）。
それまでは `startTime` / `endTime` に第1部の時刻を入れておく。コードが出たあとは `sessions` が優先されるので、そのままでよい。
